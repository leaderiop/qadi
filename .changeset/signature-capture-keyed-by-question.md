A captured signature now answers the question it was captured for. Before, `signatureObligationHandler` gave `capture` no resource, so a flow that stored what it captured stored it subject-wide: a default-scope `hasSignature` could not find it and `scope: "Any"` found it for every resource. **Breaking:** `SignatureCaptureRequest` gains required `evaluationId`, `resourceId`, `action` and `resource` (code that constructs a request must supply them; `capture` implementations just receive more), and `signatureObligationHandler` takes an `ObligationDischarge` and no longer requires `CurrentSubject`: the signer is the subject the allow was decided for. A `capture` that returns a signature for a different signer or meaning than asked now fails the discharge (`SignatureCaptureError`). **Breaking:** `signatureObligationHandler` now refuses a discharge whose question has a resource with no string id (absent, numeric, an object) with `SignatureCaptureError`, before `capture` runs, where 0.11.0 captured it and it was stored subject-wide, which a `scope: "Any"` check would then grant on every resource. A question with no resource at all still records subject-wide. New `SignatureLedger`, `signatureHistoryFromLedger`, `ledgerEntryOf` and `SignatureLedgerTest`: pass `{ ledger }` to the handler and the signature `capture` returned is recorded and read back as `SignatureHistory`; a ledger that cannot record fails the discharge. The ledger is a keyed store: an adapter implements `append(key, entry)` and `entriesAt(key)` over the opaque `SignatureLedgerKey` that `ledgerKeyOf(pair)` mints from a `LedgerPair` (a persisted format, `[1,"alice","doc-1"]`, frozen), and `signatureHistoryFromLedger` derives the exact-pair read, failing it as `SignatureHistoryUnavailable` (cause `SignatureLedgerReadError`) if the store answers a row stored under another key or signed by someone else. `checkSignatureLedger` and `checkSignatureHistoryScoping` check a deployment's real store against case-folding, trimming, Unicode-normalising, wildcard-reading and lossy mistakes, and return what they find as `LedgerConformanceViolation`s (`LedgerConformanceOptions` names a namespace for a shared table). Without a ledger, `capture` must persist where your `SignatureHistory` reads, keyed by the request.
