## Cross-cutting pitfalls (every phase)

### Pitfall X-1: A check that cannot fail

**What goes wrong:** A RED test, a type pin, a characterisation or a mutation run passes whatever the code does, so "behaviour unchanged" is asserted and never proven. This wave has six concrete ways to build one.

1. **A bare negative tstyche pin on an `Effect` or `Stream`.** The Effect language service's `floatingEffect` rule puts a diagnostic on every bare call returning an `Effect`, and tstyche reads any diagnostic as "not callable", so `expect(f).type.not.toBeCallableWith(args)` passes for *any* args when `f` returns an `Effect` (AGENTS.md §6, `NOT_CALLABLE_PIN_BUDGET`, ADR-QD-175). Every phase that adds a function returning an `Effect` (Phase 86's owner if effectful, Phase 87's shared run, Phase 89 if anyone is tempted to make admission an `Effect.fn`) and wants a refusal pin must state it through `Params<typeof f>` (or `Parameters<F>[i]`, or the declared `paramsOf` for a generic) and give it a positive twin with the same subject text. A plain-return function can keep the bare form.
2. **Hide-and-show in one tick.** `QadiProvider.lifetime.test.tsx` has a helper that does "a hide and a show that each flush synchronously, so no macrotask can fall between them" (line ~209) beside `pastTheRelease` (a real 50 ms wait, line ~162). A test written with the first helper never reaches the recycle path: it passes if `release` is a no-op, if `defer` is never called, and if the recycle is deleted outright. It is the right shape for "StrictMode double effect recycles nothing" (LT4/LT5) and the wrong shape for anything that claims a recycle happened. [read]
3. **A recording `defer` that nobody asserts on.** Phase 86's headless owner is tested "with an injected defer and no rendering". A fake `defer` that stores `run` and returns a no-op `cancel` is vacuous unless the test asserts (a) `run` was never called on a hold-in-time, (b) `cancel` was called exactly once, (c) calling the stored `run` after the cancel does not recycle, and (d) it uses a real `AtomRegistry`, not a stub (a stub registry cannot show "registry is disposed" or a reset node). [read]
4. **A RED test that is not RED.** Phase 87 opens with a RED test for `SimulationSession.ts:418` `String(exit.cause)` "against ADR-QD-182". That string form cannot throw: `v4-api-smoke.test.ts:252-276` is the canary, and `ThrownMessage.ts`'s own doc names `String` of a `Cause` as one of the three reads that stay outside `causeMessage`, "safe for its own stated reason: ... which Effect guards". So the RED can only be a *uniformity* assertion (message equals `causeMessage(cause)`), not a defect. See 87-A. [run + read]
5. **Mutation that cannot see the code.** `ignoreStatic: true` drops mutants in module-scope code that runs once at import (every Stryker config), so Phase 90's description tables and `LEAF_NEEDS` rows are invisible to Stryker; `src/react` of devtools is outside every Stryker config; `QadiProvider.tsx` is outside react's mutate list ("recorded as unmeasured", v1.10 audit). A phase that moves logic *into* one of those files makes the moved code unmeasured. See 85-D, 86-D, 88-D, 90-D. [read + prior]
6. **A scan or record script with no self-test.** v1.7 Key Lesson 1: a script that reports "0 matches" proves nothing until it has found a planted defect. Every `NN-check.mjs` for this wave needs a `--self-test` that plants the defect class (a renamed export, a type-only edit, a moved line) and fails. [prior]

**Prevention:** For each new test or script, write down in the plan the *scratch variant that must turn it RED* (delete the cancel, make `release` a no-op, make `String(cause)` throw, remove a `Match` arm, flip `export` to `export type`), run it once, and record the failing assertion text in `NN-RED-EVIDENCE.md` (the v1.10 Phase 81/82 pattern: "each part of the fix was shown load-bearing by a scratch variant"). A pin or test with no recorded way to fail does not count as evidence.
**Phase:** all; 86, 87 and 91 are the highest risk.

## Critical pitfalls

### Pitfall 85-A: "Decide the unsampled rule once" collapses three sites that do not state the same rule

**What goes wrong:** The rule is spelled at `DockModel.ts:391`, `:405` and `QuestionsPanel.tsx:112`, but the three are not the same predicate:
- `:391` (the questions join key): `unsampled: supplied === undefined && isUnsampled(status)`. It is guarded by "the host supplied questions".
- `:405` (the port-card key): `unsampled: isUnsampled(status)`, unguarded.
- `QuestionsPanel.tsx:112` `const unsampled = isUnsampled(diagnostics.status)`, consumed by `<Hydration activity unsampled>` where it only matters when `activity === undefined` (Pending vs Unwired); a *supplied* `hydration` shows `Counts` whatever the status says (`QuestionsPanel.tsx:350-370`).
A single exported `unsampled` boolean that all three read, or a view that hoists the `supplied === undefined` guard, changes which of `Pending`/`Unwired`/`Counts` shows when a host supplies a hydration reading before the first sample, and changes the questions block for a supplied-questions host. [read]
**Prevention:** The new pure hydration view takes `{ activity: HydrationActivity | undefined, status }` and returns `Counts` if `activity !== undefined`, else `Pending` if `isUnsampled(status)`, else `Unwired`: activity precedence is part of the rule, not an input. Leave `isUnsampled` (`DiagnosticsFeed.ts:87`) as the one status predicate and let the join and the cards keep their own *guards* around it; "decided once" means one function for the hydration decision and one `isUnsampled`, not one merged flag. Characterise on the phase base the 3x2 table (activity supplied / sampled-absent / unsampled-absent) x (Off, Starting, Live, Stopped sampled, Stopped unsampled) before moving anything (the existing `QuestionsPanel.characterisation.test.tsx` and `QuestionsPanel.feed.characterisation.test.tsx` are the held rows).
**Warning signs:** A test only for "unsampled and absent"; the view takes `unsampled: boolean` instead of `status`; the questions join key loses `supplied === undefined`.
**Phase:** 85.

### Pitfall 85-B: `DockFrame` still needs the status, and a derived view must keep identity or the re-render saving is zero

**What goes wrong:** `DevtoolsDock.tsx:112` reads `{ status, reading: shown } = useStoreSnapshot(model.diagnostics)` and uses `status` for `useStopNotice(status, model.diagnostics.restart)` and `shown.hydration` for one prop (`:258`). Replacing only the `shown.hydration` read with a new store while keeping the `model.diagnostics` subscription for `status` removes nothing: `DockFrame` still re-renders on every poll sample. The fix needs the status on a narrower readout too, or `DockFrame` hands the notice a status store. Second, `makeDerivedStore` (`ExternalStore.ts:197`) compares its `key()` fields with `sameFields` (identity per field) and only then recomputes; a key built from `reading.hydration` is stable only because `foldReading` (`Diagnostics.ts:144-166`) keeps a field's reference while `Equal.equals` says it is unchanged. A key that spreads a fresh object, or a `compute` that returns a new view object whose content is equal, publishes on every poll. `K extends object & Required<K>` also refuses an optional key field; state `undefined` explicitly. [read]
**Prevention:** (1) The RED/characterisation counts `DockFrame` renders across three polls whose hydration counts are equal (zero extra renders) and one poll where they differ (exactly one), and the positive twin must fail if `DockFrame` keeps the whole-reading subscription. (2) The new store is built where the other derived stores are: after `shownReading`, before any host listener (the DockModel comment at `:371-372` "Built after the shown reading and the feeds and before any host listener, so the join and the cards move first"). (3) Do not add an eighth `configure` step: the view follows `shownReading` through `parents`, as `services` does; a new step changes the `AggregateError.errors` order that BEH-QD-742 pins.
**Warning signs:** `DockFrame` still imports `model.diagnostics` for `reading`; the view's `compute` allocates unconditionally; the snapshot `!==` itself after an identical poll.
**Phase:** 85.

### Pitfall 86-A: The owner must be inert at construction, because render can run and be thrown away

**What goes wrong:** Today the registry is built in render (`registryRef.current ??= AtomRegistry.make({ initialValues: [[atoms.subject, subject], ...initialValues] })`, `QadiProvider.tsx` ~257) and the lease is built in render (`leaseRef.current ??= makeRegistryLease(...)`). ADR-QD-195 decision 1 keeps the build in render so a server render and the first client render hold the subject with no pending frame. Moving "create, seed, hold the lease" into one React-free owner is safe only if `create` allocates and seeds and schedules *nothing*: no timer, no subscription, no `defer` call. A render React discards (Suspense, concurrent render, StrictMode's first dev render on React 18 semantics) otherwise leaks a timer or a second registry; on the server effects never run, so a timer started at creation is never cancelled. [read]
**Prevention:** Only `release` ever calls `defer` (as `makeRegistryLease` does today); `create` takes `{ atoms, subject, initialValues }` and returns an owner whose first observable act is a read. Pin: constructing an owner and dropping it calls the injected `defer` zero times; `renderToString` (the `ServerRender.test.tsx` shape) of a seeded provider shows the seeded decision in the first HTML; the first client render has the subject with no pending frame (LT13/LT16).
**Phase:** 86.

### Pitfall 86-B: Effect order is the contract; "forward subject changes" tempts merging the subject write into the hold effect

**What goes wrong:** ADR-QD-195 decision 3 records, from an instrumented React 19.3.1 run, that setup runs children before the provider, so the provider's `hold` must be its **last** effect: on a reveal after a long hide, the recycle has already run in a macrotask, every consumer subscribes to the reset registry (which holds the subject, written back in `recycle`'s `finally`), and only then does the provider run its subject effect and `hold`. If the component forwards "hold, release and subject changes" to the owner from one combined effect, or declares the subject-forwarding effect after the hold, the order `subject effect -> hold` changes; with a changed `atoms` prop during the hide, `registry.get(atoms.subject)` on the new atom then happens at a different time relative to the recycle's write-back. `latestRef` has the same property: it is written in an effect ("so a render React discards never reaches it") and the recycle re-seeds from it, so moving it into the owner and updating it during render re-introduces the discarded-render leak (LT6, LT16, LT17 pin the three cases). [read]
**Prevention:** Keep three separate `useEffect`s in this declaration order: latest (`[atoms, subject]`), subject write (`[registry, atoms, subject]`, guarded by `!== subject` as now), hold/release (`[owner]`, last, `return () => owner.release()`). The owner exposes `hold`, `release`, `setLatest` (called only from an effect) and `writeSubject`; it never accepts `initialValues` after construction (LT9/LT10: a seed is not an authority and must not return after a recycle). `LT1..LT18` and the `RL1..RL10` lease tests stay **unedited** and green; new owner tests are additions.
**Warning signs:** `useEffect` count in `QadiProvider.tsx` drops; the owner has a `recycle(initialValues)`; `latestRef` assigned in the render body.
**Phase:** 86.

### Pitfall 86-C: The lifecycle matrix is StrictMode x `<Activity>` x SSR, and each cell needs a test that can fail

**What goes wrong:** The traps are exactly those named in the brief: StrictMode double effects (mount, cleanup, mount in one tick: `hold, release, hold`, so `release` defers and `hold` cancels, no recycle; a `defer` that fires synchronously in a test fake would recycle here and be a false RED/GREEN); `<Activity>` hidden longer than a macrotask (recycle fires, registry is reset *in place*, never disposed, ref never cleared); a hide shorter than a macrotask (nothing recycled); children's reveal effects before the provider's; a re-render while hidden (LT7: must keep one registry, `expected 2 to be 1` was the defect); an atoms swap while hidden (LT8: keeps the registry, reported once); an unmount (final `release` defers one recycle on a registry nobody holds; a straggler read after unmount throws nothing and leaves no node, LT14); a recycle whose `registry.reset()` throws must still write the subject back (LT18, the `try/finally`). SSR: `useEffect` never runs, so the owner on the server only ever constructs. [read]
**Prevention:** One headless test per cell with an injected defer that records `run`/`cancel`, **and** keep the LT component tests as the integration net (they use real macrotasks and real `<Activity>`). Pair every "recycles nothing" with a "recycles once" twin (X-1.2, X-1.3). React 19.2.4 (the peer floor) is not exercised; the repo installs 19.3.1 (v1.9 Known Issue), so a claim about effect order says "observed on 19.3.1".
**Phase:** 86.

### Pitfall 87-C: Publish-then-fork through a callback loses ADR-QD-194's ordering unless `try/finally` stays inside the helper

### Pitfall 91-A: Gate 13 is a presence check on names, so it cannot see the mistakes a named barrel makes

**What goes wrong:** `check-api-surface.mjs` reads declaration names with regexes. Facts that matter here, all [read]: (1) its own header says "No signature check ... a reviewer relying on this gate to catch a signature change should not"; (2) `surfaceOf` reads a barrel as `export *` lines when there are any and **otherwise** reads the index itself, so a half-converted barrel (some `export *`, some named lists) silently drops the named names from the set; loud only through STALE for documented Export-column rows, not for a `Not listed above` name; (3) `REEXPORT_NAME` treats `export type { Foo }` and `export { Foo }` identically, so it cannot tell a type-only export of a class from a value export; (4) a named list entry whose module does not declare the name passes it, only `tsc` objects. [read] The baseline today is 942 across 9 packages [run].
**Prevention:** Convert each of the three barrels in one commit (no mixed state), then run `node scripts/check-api-surface.mjs` and require the same count *as at the Phase 91 base*, which is Phase 90's end, not necessarily 942 (Phases 85-90 may legitimately add or remove an export; take the base figure at the first Phase 91 commit and record per-package sub-counts). An unexplained delta is a leak or a drop. Phase 91 adds nothing public: any new `Not listed above` row means an accidental export.

### Pitfall 91-B: `export type { X }` compiles, passes gate 13, and deletes the value

**What goes wrong:** With `verbatimModuleSyntax` a barrel must use `export type {}` for types and `export {}` for values. A same-name type-and-value merge (`export type Policy = typeof Policy.Type` beside `export const Policy`, the Schema-first idiom of AGENTS.md §7) is exported with `export { Policy }`, which carries both meanings; `export type { Policy }` carries only the type. So does a class (`Data.TaggedError`, `Context.Service`, `Schema.TaggedError`: 41 `export class` in core). In the barrel modules a same-name declaration appears twice for about 34 names in core (two of them, `createPermissionGroup` and `tabulatePorts`, are function overloads, the rest type+value merges: `ActedResult`, `DecisionStreamEvent`, `DecisionStreamSynced`, `DecisionWire`, `EncodeRefusal`, `Matcher`, `ValueRef`, `Obligation`, `ActionName`, `Combining`, `EventName`, `FieldStrategy`, `HistoryScope`, `LabelName`, `Policy`, `RelationName`, `RoleName`, `RuleEffect`, `KeyRefusal`, `PortReply`, `PortWireRefusal`, `PortWireReply`, `RemotePortFailure`, `RelatedResult`, `RoleStep`, `Signature`, `SinkRecordJson`, `StoredRecordJson`, `DecodeRefusal`, `FilteredSubjectOutcome`, `SubjectOutcome`, `UntrustedRefusal`, `createPermissionGroup`, `tabulatePorts`), `DecisionOutcome` in react, and seven in audit (`ArchiveRefusal`, `AuditPortReply`, `AuditWriteOutcome`, `UnwrittenStaging`, `WrittenStaging`, `RetentionInputRefusal`, `LedgerConformanceViolation`) [run, uniq-d over barrel modules]. The wrong direction (`export { OnlyAType }`) is a TS1205 compile error; the dangerous direction is silent unless some consumer in the repo uses the name as a value, and gate 14's consumer probes only a sample (`make*Feed`, `DecisionCacheShape`). [read + run]
**Prevention:** Generate the three barrels from the compiler, not by hand: for each module in the old barrel, `ts.createProgram` + `checker.getExportsOfModule` and emit `export { ... }` when the symbol has a value meaning and `export type { ... }` otherwise; sort by module path (`barrel-order`, ASCII, case-sensitive). Then a record script `91-surface-diff.mjs` dumps `{ name, flags: value|type|both }` for every export of the three packages' root *at the Phase 91 base and after*, fails on any difference, and has a self-test that plants a type-only export of a class. Run it after each barrel commit, not once at the end. Do the same for `@qadi/react`'s `components.tsx` and `hooks.ts` ("deliberate multi-export grouping files": each export now needs its own line).

### Pitfall 91-C: Folding a visibility-only file can create a madge cycle, and one of the four named folds does

**What goes wrong:** ADR-QD-037's gate counts type-only edges, and every cycle-breaker in this codebase says so (`QadiProvider.tsx` re-exports `InitialValues` "declared in `HydrationEngine.ts` so the engine imports nothing from this file (a type-only import still counts as a madge cycle)"). HydrationEngine.ts ...`. `Hydration.ts` imports `QadiAtoms` (type) for `hydrateDecisions(..., atoms)`. Folded, `HydrationEngine.ts -> QadiAtoms.ts -> HydrationEngine.ts`. It folds only if the atoms parameter's type is stated without importing `QadiAtoms.ts` (a structural `HydrateTarget` in `HydrationEngine.ts`, which `QadiAtoms` already satisfies) or the file stays and the ADR records the rejection. Re-run the graph on the *Phase 91 base*, not on the numbers above: Phases 85-90 edit these packages.

**What goes wrong:** `SPAN_KEY_SHARED = "packages/core/src/PortSpanEncode.ts"` and `SPAN_KEY_DECLARATION = ".../EvaluationSpan.ts"` are constants in `check-house-style.mjs` (~2438-2441). `[span-key-source]` extracts keys from the declaration, reads `sharedQuestionKeys.subjectId` from the shared file, and fails with "spells the shared key" if the declaration file spells it; with both in one file the shared key is spelled in the declaration and the rule fails (or, if the constants are edited to the same path, the "first mention is allowed in SHARED" branch is skipped by `if (rel === SPAN_KEY_DECLARATION) continue`). ### Pitfall 91-E: TS2883 shows up in declaration emit of *other* packages, not in the one that changed

**What goes wrong:** TS2883 ("inferred type cannot be named without a reference to ...") appears when an exported declaration's inferred type refers to a symbol that the emitting file cannot name through a module specifier that consumers can resolve. For a cross-package case that is a core type that `@qadi/core`'s root does not export; AGENTS.md §9 already says "re-export internal types explicitly where `.d.ts` emission needs to name them (TS2883)" and `react/Hydration.ts` carries exactly such lines (`export type { HydrationDrop, HydrationDropReporter } from "./DeveloperSignals.ts"`, `export type { DehydrateOptions, HydrateOptions } from "./HydrationEngine.ts"`, "so `.d.ts` emission has to be able to name what `HydrateOptions` refers to"). [read]
**Prevention:** After each barrel commit run `pnpm build` (the shipped graph) and `pnpm typecheck`, then `pnpm spec:package` (packs and compiles a consumer through the published `exports`).
