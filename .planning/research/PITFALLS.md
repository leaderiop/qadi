## Critical Pitfalls

Mistakes that cause a rewrite, a lying type, or a silent behaviour change.

### Pitfall 1: A type-only brand that an exported schema, a spread or an `as` can mint
**What goes wrong:** `AuditEntry` is today `typeof AuditEntry.Type` of a `Schema.Struct` (`packages/audit/src/AuditEntry.ts:56-59`), and the barrel does `export *` (`packages/audit/src/index.ts:3`), so the schema const is public. Effect 4.1.2's `Schema.brand` "only narrows the TypeScript output type. It does not change the schema's runtime AST or add runtime checks" (`node_modules/effect/src/Schema.ts` ~5298-5320). A branded schema still has `make`/`makeEffect` (`Schema.ts:291`), so `AuditEntry.make({...})` mints a "branded" row from the **lenient** struct. The existing doc comment already warns that this schema alone "strips a typo'd field inside the embedded policy rather than refusing it" (`AuditEntry.ts:17-21`). The brand would then say "only the codec makes this" while the lenient schema, a spread, or `as` makes it too.
**Spread hole (specific to this codebase):** with an intersection brand, `{ ...entry, sequenceNumber: 1.5 }` keeps the brand symbol key in its inferred type, so it type-checks as `AuditEntry` with a non-integer `sequenceNumber`. The tests do exactly this today (`packages/audit/test/ArchiveFacts.test.ts:21` `entriesWith`). If the brand lets that compile, deleting the write-path integer check ("Write-path `SequenceNumberInvalid` becomes a type error") is unsound: `ArchiveFacts.ts:103-108` is the only thing refusing `1.5` or `2 ** 53` today.
**Why it happens:** the review's "ARCH-112's admit move" is only half-transferable. Phase 65 needed a private constructor **and** a private instance member, "because a private constructor alone still lets a same-shape object literal type-check" (`.planning/milestones/v1.7-phases/QD-65-only-admit-builds-an-admitted/65-CONTEXT.md`, "Construction lock"). A `Schema.brand` has neither.
**Consequences:** a brand that does not enforce its claim; `as`/`!` pressure (forbidden by AGENTS.md section 6) in tests and in the codec; the integer check deleted while a spread still bypasses it.
**Prevention:**
- Mint the value in one place with no `as`: the Phase 65 form (class with `private` ctor plus a `declare private readonly` marker; probe which compiles under this tsconfig and record the probe), built only inside `AuditEntry.ts` by `encodeAuditEntry` and `decodeAuditEntry`.
- Do not export a schema whose `.make`/decode can mint the brand. Export the type, the two codec functions and, if a wire shape is needed, an un-branded schema under a different name.
- If `sequenceNumber` stays `number`, either brand it too (`Int`) or keep the `Schema.Int` check in `archiveFacts` and drop only what the type really proves. Do not delete a check the type cannot enforce.
- Two refusal pins like Phase 65: `@ts-expect-error` **plus** tstyche `toRaiseError(<code>)`, each with a positive twin on the codec. Never `not.toBeConstructableWith` (reason-blind; see Pitfall 10).
**Detection:** a test that spreads a branded row with `sequenceNumber: 1.5` and passes it to `archiveAuditTrail` compiles. `grep -n " as \|!\." packages/audit/src/AuditEntry.ts` shows a hit.
**Phase:** 77.

### Pitfall 2: Brand changes the runtime shape that `holds`, `planPurge` and the stores rely on
**What goes wrong:** `VerifiedArchiveImpl.holds` counts copies in a `MutableHashMap<AuditEntry, number>` "by structural equality" (`AuditArchive.ts:243-250`), and `planPurge` does the same (`Retention.ts:137`). Effect 4.1.2's `Equal.equals` is structural for plain objects (`node_modules/effect/src/Equal.ts:186-300`) and `Hash.hash` hashes structurally and **caches per object** in a `WeakMap` (`Hash.ts:108-140`). If the brand becomes a class instance, equality and hash still walk own enumerable keys **[verify]**, but a class with an extra own field, a `toJSON`, or an `Equal` implementation changes what `JSON.stringify(entry)` writes to the store ("`JSON.stringify(entry)` puts exactly the bytes the decision stream emits", `AuditEntry.ts:12-16`), and what a purge compares. A host's store row (plain `JSON.parse`) is no longer assignable to the type, so the host's own `planPurge(entries)` call needs `decodeAuditEntry` on every row it reads.
**Why it happens:** the brand is introduced for type safety and nobody re-reads the runtime consumers.
**Consequences:** a purge that selects nothing (rows no longer equal the archive's) or, worse, a class instance that compares by reference and silently makes `holds()` return 0 for every row; a changed stored byte shape.
**Prevention:** write the characterisation first: `JSON.stringify(entry)` byte-identical before and after, `holds()` and `planPurge` agree for a decoded row, a re-decoded row and a row from a different decode call (`packages/audit/test/ArchiveRoundTrip.test.ts`, `Retention.test.ts` already hold the shapes). Keep the instance own-keys exactly `record` and `sequenceNumber` (the key may be absent vs `undefined`: `encodeAuditEntry` writes `sequenceNumber: undefined`, a decoded row without one omits or sets it; pin which).
**Detection:** `ArchiveRoundTrip`/`Retention` tests go red only on a rebuilt-row case, not on the same-instance case; check both.
**Phase:** 77.

### Pitfall 3: "Envelope-first" decode reorders refusals and breaks the `unwalked`/`TooDeep` contract
**What goes wrong:** today `decodeAuditEntry` decodes `record` first through core's `decodeSinkRecordWithJson` and then the row with `record` `unwalked` (`AuditEntry.ts:107-117, 135-158`), and `readAuditArchive` decodes its own envelope with `entries` `unwalked`, then each entry from its own root (`AuditArchive.ts:290-330`). Flipping to envelope-first changes which refusal wins for an input that is wrong in two places (an unknown row key and a record at `version: 3`; a row nested past `MAX_DECODE_DEPTH` outside its record and a bad record). `EntryNotDecodable.refusal` is part of the public `ArchiveRefusal` union.
Two precedents show how easy the details are to get wrong: `unknownKeys: "ignore"` drops index-signature keys silently (Phase 57 WR-01, `.planning/milestones/v1.6-phases/QD-57-untrusteddecoder-states-the-envelope-s-unknown-key-policy/57-REVIEW.md`), and a pending changeset already documents a deep unknown record key (`.changeset/audit-deep-unknown-record-key-ignored.md`).
**Why it happens:** two decoders each own half of one input; the order is part of the observable behaviour.
**Consequences:** an existing refusal test flips without anyone deciding it; a `TooDeep` that used to be `EntryNotDecodable` at an index (the doc at `AuditArchive.ts:110-117` states that distinction).
**Prevention:** a characterisation matrix on the phase base (RED/characterise before the edit, Phase 52 style: keep the file byte-identical across the phase): rows for each pair of simultaneous defects, recording the refusal that wins. Decide the order in the ADR amendment, not in the code. Keep `UNTRUSTED_DECODE_BUDGET` in mind (Pitfall 9): any new `Schema.decode*`, `JSON.parse`, `onExcessProperty` or `exceedsJsonDepth` token in `packages/audit/src` fails the gate unless the budget and the AGENTS.md table move together; reuse `untrustedDecoder`.
**Detection:** `packages/audit/test/AuditEntryDifferential.test.ts`, `UntrustedSeams.test.ts` and `AuditArchive.test.ts` change expectations in the diff.
**Phase:** 77.

### Pitfall 4: The RED test for "the archive that cannot be read back" may not reproduce, or may pin the wrong half
**What goes wrong:** the review says the gap "is read from the code, not yet reproduced". Reading the code, the writer-versus-reader mismatches I can name are: (a) `archiveAuditTrail(entries, now)` accepts any `now`, and `ArchiveEnvelope.metadata.createdAt` is `Schema.Number`; a `NaN` or infinite `now` becomes `null` under `JSON.stringify`, and the reader refuses the stored bundle as `Malformed` (`AuditArchive.ts:196-206, 278-287`). A brand on **entries** does not touch this. (b) a hand-built entry whose `record` is typed-valid but not core-decodable (a `resource` or `HasCustom.params` nested past the decode bound, or a record that `encodeSinkRecord` accepts but `decodeSinkRecordWithJson` refuses) is archived by the writer and refused by the reader as `EntryNotDecodable`. (c) `keyMaterial` passes through unchecked both ways. (a) and (c) are archive-level, (b) is entry-level. **[verify]** each by running it; none was executed here.
**Why it happens:** the planner writes one RED test for the headline and ships a brand that closes (b) only; or no input reproduces, and the phase invents a defect to justify the change.
**Consequences:** a "live defect fixed" claim that is half true; or a Breaking change with no RED.
**Prevention:** the opening task enumerates writer inputs across the **whole** archive (entries, `now`, `keyMaterial`), runs `readAuditArchive(JSON.parse(JSON.stringify(archive)))` for each, and records every refusal. If none reproduces, record a "refuted at the base" disposition as v1.3's ledger did (`RETROSPECTIVE.md`, v1.3 "a third disposition, refuted") and say the brand is a deepening only. A RED test must be written without `as`: build the bad entry through the public codec or `@ts-expect-error`, and prove it fails on `ab8ccb75` before the fix (`NN-RED-EVIDENCE.md` is the house form).
**Detection:** the RED test passes on the base; or goes green after a change that touches only entries while `createdAt: NaN` still round-trips badly.
**Phase:** 77 (first plan).

### Pitfall 5: Removing `init` makes the first renders show an unconfigured model (the Off -> Starting transient)
**What goes wrong:** `useScoped` builds in a layout effect and publishes the value with `setValue` (`packages/devtools/src/react/useScoped.ts:20-47`). Today the model is built **with** its inputs (`useDockModel.ts:51-57`, `useDiagnostics.ts:41`, `useTimeline.ts:60-67`), and a separate layout effect re-runs `configure` on the render the model appears. With "build empty, configure only", the render in which the model first exists reads an empty model: `DiagnosticsFeed` is `Off` until `configure` runs (`DiagnosticsFeed.ts:130-213`), `Starting` after. Effect order is children first, then the parent hook's `useLayoutEffect`, so every child's layout effect and first `useSyncExternalStore` read sees the unconfigured model, and the commit re-renders synchronously with `Starting`. Nothing paints wrong, but a render-recording test sees two renders, `DiagnosticsNotice` and `diagnosticsRootProps(status)` flash an `Off` state ("no options handed over"), and `isUnsampled(Off)` is `false` (`DiagnosticsFeed.ts:96-103`) so the questions join (`DockModel.ts` `joinInputOf`, `unsampled`) briefly claims "not handed over" instead of withholding. Today's `idleDiagnostics(options)` exists precisely to avoid this (two constants keyed on whether options were given, `DiagnosticsFeed.ts:122-131`).
**Why it happens:** "scope, then configure" as two effects instead of one step.
**Consequences:** a visible change in the first-render sequence; the hidden-claim flash on the Questions panel; a StrictMode run that shows it twice.
**Prevention:**
- The review already says to pin this "with a characterisation test first". Do it on `ab8ccb75` for `useDiagnostics`, `useTimeline` and the dock: record the exact sequence of (status, reading) values a probe component renders, with and without options, plain and under `StrictMode` (`packages/devtools/test/react/useDiagnostics.test.tsx`, `TimelineLifetime.test.tsx:67`, `DevtoolsDock.test.tsx:1275` are the nearest existing shapes). Decide in the ADR whether the sequence changes; if it must not, `configure` inside the same layout effect that builds, before `setValue`, so the model is published already configured.
- Keep `idleDiagnostics`/`idleTimeline*` unless the new sequence provably makes them unreachable; deleting them is the stated payoff ("Delete idle stand-ins"), so make deletion conditional on the characterisation staying green.
**Detection:** the characterisation shows an extra `Off` row, or `DiagnosticsNotice` tests (`DiagnosticsNotice.test.tsx`, `DiagnosticsScreens.test.tsx`) see the "none handed over" text during mount.
**Phase:** 79 (opens with the characterisation, as the roadmap says).

### Pitfall 6: Folding `configure` into the build uses stale props after a hidden `Activity` (or StrictMode) rebuild
**What goes wrong:** `useScoped`'s `make` is "read once per mount" (`useScoped.ts:44-45`); the effect has `[]` deps. Today that is safe only because the **second** effect re-applies the latest inputs whenever `model` appears (`useDockModel.ts` comment: "It runs again on the render the model appears, so a prop changed in between still lands"). A hidden `Activity` runs the cleanup (closes the scope, `setValue(undefined)`), keeps state, and on show re-runs the effect with the **first render's** `make` closure. If the new hook configures only inside the build, a dock hidden through a prop change comes back with the stale inputs until the next change.
**Why it happens:** collapsing two effects into one removes the only place the current props were read.
**Prevention:** the hook must read the latest inputs at build time (a ref written in render or in a layout effect, as `QadiProvider.tsx` already does with `signalRef.current = onDeveloperSignal`) or keep the post-build configure effect and rely on an idempotent first configure. Whichever is chosen, the test is: mount with props A, hide in an `Activity`, change to B, show, assert the model holds B. Also assert StrictMode builds twice, closes the first, and configures only the live one (`TimelineLifetime.test.tsx` L1 states the existing pattern).
**Detection:** the new hook has no ref and no second effect; the Activity test is absent.
**Phase:** 79.

### Pitfall 7: The "one per-field identity rule" reuses `sameFields`, whose contract differs from the feeds' contract
**What goes wrong:** `makeDerivedStore`'s `sameFields` (`packages/devtools/src/model/ExternalStore.ts:107-122, 145`) differs from the feeds' hand-written `!==` lists in four ways, and each is a behaviour change:
1. **Omitted vs `undefined`.** `sameFields` uses `Object.entries` and counts "a field on one key only" as a change; the feeds read "an omitted input as `undefined`" (`TimelineFeed.ts` configure doc; `DockModel.ts` `DockModelInputs`). `configure({source})` then `configure({source, capacity: undefined})` would read as a change. For the timeline that is a **resize that empties the buffer and restarts the read** (`TimelineFeed.ts:178-193`).
2. **Optional fields.** `makeDerivedStore` constrains `K extends object & Required<K>`; the compiler refuses an optional field (doc at `ExternalStore.ts:130-132`). `DockModelInputs`, `TimelineFeedInputs`, `GatesFeedInputs` are all optional-field interfaces. Reuse needs a normalising step (every key always present), not a type loosened to `Partial`.
3. **Nested diagnostics options.** The dock's `diagnostics` is an object that hosts write inline; the contract is "restarts when `layer`, `collector` or `intervalMillis` changes identity, never when the options object does" (`useDiagnostics.ts` doc, `DiagnosticsFeed.ts:182-198`). Top-level identity on `diagnostics` restarts the poll every render for an inline literal; flattening to the three fields loses the **`undefined` vs `{}`** distinction (`{}` is the one-token opt-in that must start the poll; `undefined` is `Off`), so `undefined` -> `{}` would compare "equal" and nothing would start.
4. **Same input, two consumers.** `diagnostics.intervalMillis` also feeds the gates feed (`DockModel.ts`: `intervalMillis: inputs.diagnostics?.intervalMillis`), and `reading` is never a restart input at all (it recomputes the merge through `shownReading.refresh()`). A single table keyed by dock input must say which feed each field restarts.
Also: `sameFields` itself had a bug found in Phase 72 review (it walked inherited keys; WR-01, `.planning/milestones/v1.8-phases/QD-72-a-derived-store-behind-the-dock-model-s-stores/72-REVIEW.md`). Own-key semantics are now pinned; do not reintroduce a prototype-walking variant.
**Prevention:** one table test per feed, one row per field moved alone, **plus** rows for omitted-vs-`undefined`, `undefined`->`{}`, an inline-equal diagnostics literal, and `capacity: undefined` vs `capacity: DEFAULT_TIMELINE_CAPACITY` (today a different identity and therefore a wipe; decide and pin whether it stays one). Keep `Required` and normalise inside the rule's one caller. Add a compile-time pin that a new `DockModelInputs` field cannot be omitted from the rule table, which is the review's stated payoff ("a new field compiles and silently never restarts").
**Detection:** a timeline that empties when a host re-renders with a re-spelled but equal input; the diagnostics test "does not restart on a re-render with a fresh but equal options literal" (`useDiagnostics.test.tsx:82`) goes red.
**Phase:** 79.

### Pitfall 8: Resizing a store in place loses the pause reset, the listener-throw guarantee, or the closed-scope guard
**What goes wrong:** today a capacity change builds a new inner `TimelineStore` and publishes through the mirror (`TimelineFeed.ts:178-193`). Three properties live in that exact code and are easy to drop when `resize` becomes a store command:
1. **Pause reset.** The new inner store starts unpaused; `usePaused` reads `isPaused` through the same subscription (`useStoreSnapshot.ts:20-25`) and only hears a pause change on a `publish`, never on a `set` of an equal reference. The spec text says "empty at the new bound, reset pause" (review candidate 2). `resize` must `publish` (not `set`) so a paused-then-resized store notifies. `makeTimelineStore.setPaused` already carries a comment saying this (`TimelineStore.ts:76-81`).
2. **Listener throw.** ADR-QD-177 (Phase 64): every listener runs and what they threw is rethrown after. The feed wraps the resize publish in `try { push() } finally { readSource(next.source) }` so a throwing listener cannot skip the read that refills the emptied timeline; Phase 64's WR-01 found exactly that skip (`.planning/milestones/v1.7-phases/QD-64-one-throwing-listener-cannot-silence-the-rest/64-REVIEW.md`), pinned by `.changeset/devtools-capacity-change-reads.md`. If `resize` publishes inside the store and the feed calls it bare, a throw escapes before `readSource`: an empty timeline with status `Reading` and nothing reading.
3. **Closed scope.** Phase 60 WR-02: `TimelineFeed.configure` once had no closed-scope guard and published `Reading` and emptied the timeline after the scope closed (`.planning/milestones/v1.6-phases/QD-60-devtools-headless-interface-is-the-feeds/60-REVIEW.md`). The `reads.closed()` guard at `TimelineFeed.ts:171` must stay in front of `resize`.
**Also:** "one publish per record, not two" changes how many times a subscriber is told per record (today inner `view.set` plus the feed's `push` -> `view.publish`). Any test or host that counts notifications changes; the DockModel subscription (`timeline.subscribe` -> `spread`) must still run first and exactly once per shown timeline.
**Identity of a kept store:** the point of the change is that `timeline` is the same object across a resize, so every subscriber (`useStoreSnapshot`, `usePaused`, `DockModel`) keeps its subscription. A subscriber added during the resize publish is called in the same pass (listener contract, `ExternalStore.ts` header); a `resize` that swaps the inner `view` store instead of calling `publish` on the same one would orphan every listener. Do not give `resize` its own listener set.
**Prevention:** the characterisation file for Phase 78 keeps the six forwarded members' observable behaviour: pause reset on resize, throw-then-still-reads, closed-feed no-op, snapshot identity preserved by an equal-capacity `configure`, `restart` after resize reads the **current** source, and notification counts per record. Add `resize` tests that need no scope or source (the review's stated benefit) and run them with a throwing listener. Keep `idleTimeline` honest: it has six members and must grow `resize` (or the type must not require it for the idle stand-in) or the interface shows a seventh member the idle store lacks.
**Detection:** a resize test with a throwing listener shows `status` `Reading` and zero records after; `TimelineFeed.test.ts` and `TimelineLifetime.test.tsx` change expected counts.
**Phase:** 78.

### Pitfall 9: Mutation score regression on the files this wave deletes branches from
**What goes wrong:** Phase 72 recorded "`DockModel.ts` keeps its mutation score of 1" (`.planning/PROJECT.md` v1.8, Phase 72 bullet; ADR-QD-168). The devtools `model/` files are inside Stryker's mutate set (the lens is moved there **so that** it is "held to the mutation gate", review candidate 3); `react/` is not. Removing `init` branches and the three `!==` lists, and adding the rule table, shifts mutant ids and creates new surviving ones. Past waves lost points exactly here: surviving mutants on review-written lines (Phase 76: "12 survivors on review-written lines were unpinned path arguments", `RETROSPECTIVE.md` v1.8), mutant ids that move when a line is re-wrapped (v1.6 audit: "re-wrapping moves the D-16 mutant ids"), and a pre-review score read as the final one (v1.4 lesson 1).
**Prevention:**
- Commit a per-file Stryker baseline (`NN-mutation-base.json`) on the untouched base, alone and first, for `DockModel.ts`, `TimelineFeed.ts`, `TimelineStore.ts`, `DiagnosticsFeed.ts`, `GatesFeed.ts`, `ExternalStore.ts`, `AuditEntry.ts`, `AuditArchive.ts`, `ArchiveFacts.ts`, `Retention.ts`; compare with the same invocation at close **after** the last review fix and record the post-review figure (`NN-mutation-review.json`).
- Add tests at the new seam before deleting the old ones (`_SHARED-CONTEXT.md`: "plans must not lower the Stryker score of touched files").
- A new `LensSession` file starts at no baseline: set its own bar (score of 1 like `DockModel.ts`, or record why not) up front, since the file is new and a "no drop" check passes vacuously.
- Mind `ignoreStatic` (Phase 57 pitfall, noted in `65-CONTEXT.md`): static mutants are excluded by default; a rule table of constants can hide untested rows.
**Detection:** `compare` exits non-zero; or a new file has no baseline row.
**Phase:** every phase; 78/79 are the highest risk (they delete branches from `DockModel.ts` and the feeds).

### Pitfall 10: A negative type pin that cannot fail, or one that moves a budget row without the table
**What goes wrong:** v1.7 Phase 62 found 86 pins in 27 files where `not.toBeCallableWith` on an Effect-returning subject passed whatever the arguments (the Effect language service's `floatingEffect` diagnostic). AGENTS.md section 6 now budgets every such pin in `NOT_CALLABLE_PIN_BUDGET`, checks it both ways and requires a positive twin with the same subject text (`[not-callable-control]`). This wave adds pins that fit the vacuous class: "`makeTimelineFeed` no longer takes an init" (an Effect-returning `Effect.fn`), "`AuditEntry` cannot be built from a literal", "`QadiContextValue` has no `instrument`". Existing pins in `packages/devtools/test/surface.tst.ts:302-306` assert `makeDiagnosticsFeed({ intervalMillis: 1_000 })` has a type; that line must change when `init` goes (it is the public signature).
**Prevention:** for an Effect-returning function, refuse through `Params<typeof f>`; for the brand, `@ts-expect-error` plus `toRaiseError(<code>)` probed against the real compiler (Phase 65's rule: "the code, not a message, is the check"); every new negative pin gets a same-subject positive twin and one deliberate break shown red once; any added `not.toBeCallableWith`/`not.toBeConstructableWith` row edits `scripts/check-house-style.mjs`'s budget **and** AGENTS.md's table together.
**Detection:** `[not-callable-pin-table]` or `[not-callable-control]` fails; or a pin passes with the argument changed to a valid one.
**Phase:** 77 (brand), 79 (feed signatures), 80 (`instrument`).

### Pitfall 11: Gate 14 fixture and docs fences still call `make*Feed(init)`
**What goes wrong:** gate 14 compiles and **runs** a consumer against the packed `exports` map and fails if a `make*Feed` is left unprobed (`scripts/check-package-install.mjs:60-69, 647-728`). Its fixture is a template string that calls `makeTimelineFeed({ source })`, `makeGatesFeed({ gates })`, `makeDiagnosticsFeed({})`, and asserts `Reading`, `Unwatched`, `Read`, `Starting`/`Live`, listener counts and release on close. Removing `init` makes each of those lines a type error inside the sandbox (reported by gate 14, not by `pnpm typecheck`, so a green local typecheck hides it). Docs compile too: `packages/devtools/README.md` (the Phase 60 WR-01 finding was precisely that the README's headless example subscribed after the build and missed a stop reached during the build), `apps/website/src/content/docs/docs/packages/devtools.md`, `spec/behaviors/28-devtools-screens.md`, ADR-QD-047/169/173 fences (`check-doc-examples.mjs`, `check-website-doc-examples.mjs`). Moving the first action from the build to `configure` moves the window where a stop can occur: a subscriber must now be registered **before** `configure`.
**Prevention:** edit the fixture to `build bare, subscribe, configure(...)`, keep every `expect(...)` line and the "feed must actually run the call" accounting; confirm it still fails when a feed call is dropped (the gate's own self-check). Grep before closing: `makeTimelineFeed(`, `makeGatesFeed(`, `makeDiagnosticsFeed(`, `makeDockModel(` with an argument across `packages/devtools`, `spec/`, `apps/website/src/content`, `scripts/` (about 208 occurrences in tests alone; the review counts "~190 test constructions"). `spec/overview.md` rows for the three feeds and `*FeedInputs` types change with the signatures (gate 13, count 940 at v1.8).
**Detection:** `pnpm spec:package` (gate 14) fails after `pnpm check:pr` steps before it passed; or `pnpm spec:examples`/`spec:website-examples` fail.
**Phase:** 79.

## Moderate Pitfalls

### Pitfall 12: The lens session persists what the DOM adapter used to discard
**What goes wrong:** `useLens` keeps `highlighted`, `picking` and `picked` in `useState` (`packages/devtools/src/react/useLens.ts:43-120`), so a tab switch (panel unmount) clears all of it and `Escape`, pointer and click listeners exist only while the panel is mounted. Moved into the dock model, state outlives the panel:
- `picking` can be `true` while no document listener exists (another tab is shown), so the toolbar says "picking" and Escape does nothing; on return the button is stale. The spec says "opening the inspector exits lens mode" (`spec/devtools-spec/01-shell.md:72`): the dock session and lens session need an explicit rule for a tab change, decided and pinned, not left to unmount ordering.
- `picked` survives a tab switch (the review says that is the point, "Pick survives a tab switch"), but `InstanceRow` calls `scrollIntoView` in an effect on `[picked]` (`QuestionsPanel.tsx:~245-255`) and an effect fires on mount: returning to the tab re-scrolls to the old pick every time. Needs a consumed/once semantic or an explicit decision that it should scroll.
- A stale picked id (guard unmounted while the tab was away): the review says the session "Decides a stale picked id". INV-QD-107 already has the rule ("an item that left the list stays shown and is marked as no longer there", `spec/invariants.md:3388-3410`) and `HeldChoice.ts` implements it. Reusing `resolveHeld` is the consistent choice; inventing a second staleness rule is the defect this series keeps removing.
- The overlay: panel cleanup calls `clearLens(document)`; with `highlighted` retained the next mount redraws it unasked ("A screen never changes what it shows without the reviewer").
**Prevention:** write the lens rules as plain calls first (toggle clears both; hover over nothing clears; `Escape` cancels picking and highlight, not the pick; choose returns whether it handled the click) as a characterisation of the **current** hook through `QuestionsPanel.gates.test.tsx:267-410`, then move the same rows to the model file unchanged; every row that changes (persisted pick, stale id) is a named decision in the ADR.
**Phase:** 80.

### Pitfall 13: The adapter decides the swallow, or reads stale instances
**What goes wrong:** `choose` swallows the click (`preventDefault`, `stopPropagation`) **only if** `gateIdAt` found a guard, otherwise the dock's own controls stop working the moment picking is on (`useLens.ts:62-74`). It runs in a **capture** listener, synchronously. If the session decides after a store notification or effect, the page's own handler has already run. The session's `choose(id | undefined)` must return the decision synchronously and the adapter must act on the return value inside the listener. Likewise the listeners must read the *current* picking flag and instances at event time: today the effect re-subscribes on `[picking, instances]`; a session-driven adapter that closes over a render's snapshot reintroduces the stale-closure class (`QuestionsPanel.thunk.test.tsx` and `.feed.characterisation.test.tsx` pin the instance-refresh shape).
`useLens`'s `highlighted` effect measures after commit on purpose ("so the boxes are computed after React has committed", `useLens.ts:46-58`); an adapter that draws from the store notification, before React commits the guard that just changed, measures the old DOM.
**Prevention:** keep `Lens.ts` (all DOM measuring, drawing, hit-testing) untouched and `@qadi/react` DOM-free (AGENTS.md section 13); the adapter keeps three listeners and one draw effect, the session holds ids only (not elements, not instances: the model carries `element` as `unknown` on purpose, `Lens.ts` header). `Lens.test.ts` stays byte-identical.
**Phase:** 80.

### Pitfall 14: Removing `QadiContextValue.instrument` is a public, Breaking change in a package the wave otherwise leaves alone
**What goes wrong:** `packages/react/src/index.ts:6` is `export * from "./QadiProvider.tsx"`, so `QadiContextValue` and `useQadiContext` are public (the file's own comment says "not part of the package's public surface", which the barrel contradicts). `spec/overview.md:570` lists `QadiContextValue`. The `value` memo has `instrument` in its deps (`QadiProvider.tsx:306-309`); removing the field must also remove it from the deps without dropping the `gateScope`/`writer` path (the writer is already resolved once and lives on `GateScopeContext`, ADR-QD-111, `spec/decisions/111-a-gate-writer-is-resolved-once-by-its-provider.md`). Doc comments name the field in `QadiProvider.tsx:91`, `useGate.ts:139`, `GateRegistry.ts:24`. The v1.8 lesson applies: a tidy edit of a decision record can change its provenance sentence; ADR-QD-111's text must be amended, not silently rewritten.
**Prevention:** the roadmap allows "removed, or the reason it stays is recorded": first grep every reader (`packages/*/src`, `packages/*/test`, `apps/`, `examples/`, `features/`, website docs) and record the result; if removed, it is a `@qadi/react` minor marked **Breaking** (changeset text starting `**Breaking.**` as in `.changeset/devtools-feed-hands-the-gate-registry.md`), an `apps/website/.../reference/upgrading.md` entry under the current `0.13:` heading series, gate 13 (`spec/overview.md`'s row text), a `@ts-expect-error` + `toRaiseError` pin that the field is gone, and no change to `useMemo` identity behaviour for `atoms`/`registry`/`gates` consumers (`packages/react/test/GateRegistry.test.tsx`). The `fixed` group in `.changeset/config.json` versions all packages together, so the bump kind still has to be written per package.
**Phase:** 80.

### Pitfall 15: Spec registers, ids and the changeset/guide chain
**What goes wrong:** every wave edits the same registers (`spec/README.md` CCR tail, `spec/invariants.md`, `spec/traceability.md`, `spec/overview.md`, `spec/decisions/index.yaml`, devtools behaviour docs), and a mismatch fails a named gate: `[no-numbering-placeholder]` (placeholders such as `ADR-QD-NEXT`), ADR `Document ID` equal to the file number (gate 10 per `_SHARED-CONTEXT.md`), `spec-revise --check`, `verify-traceability --strict`, `check-devtools-claims.mjs` (gate 12: every new "not built/does not" sentence in `spec/devtools-spec/` needs a row in "Claims of absence"), `check-api-surface.mjs` (gate 13). Recurring review findings of the same class in every wave: a spec sentence overclaims what the code or tests do (72 WR-02/WR-05, 73 WR-02/WR-03, 74 WR-01/WR-02/WR-03, 60 WR-01/WR-02), a CCR row cites the wrong register revision (74 WR-02), a spec says a file "does not change" and the phase revised it (74 WR-03), and a **plan-local id** (D-NN, REQ-NN, phase numbers) leaks into shipped source, test titles or scenarios (v1.5 audit: about 20 left; 74 WR-07).
Wave 14 has no `_WAVE14-CONTEXT.md`, hence no reservation table: using `scripts/next-id.mjs` in this wave contradicts the standing "never run it, use reserved ids" rule, and picking numbers ad hoc races across the four serial phases. Next free on disk: ADR-QD-190, CCR-QD-469, BEH-QD-721, INV-QD-399; ARCH-124..127.

Claims in spec are stated at the strength the tests give them; list what enforces each (compiler, test, review), as ADR-QD-185 does. Each phase's closing SUMMARY lists `requirements-completed` itself (v1.8 lesson 3, v1.5 lesson 1).
**Phase:** before 77, then each phase's records plan.

### Pitfall 16: Serial phases that edit each other's covered files go stale, and phase-private guards break silently
**What goes wrong:** Phase 78 edits `TimelineFeed.ts`, Phase 79 edits it again plus `DockModel.ts`, `GatesFeed.ts`, `DiagnosticsFeed.ts`, `useScoped`-using hooks, Phase 80 edits `DockModel.ts` again. Verification covers files by digest; the retrospective counts stale phases at close in **every** milestone (v1.0: 4, v1.3: 6, v1.5: 5, v1.8: 6) and v1.8 found a real break: "`75-contract-check.mjs` exiting 1 at HEAD" because a later phase put a module-load call into a shared test helper (`.planning/milestones/v1.8-MILESTONE-AUDIT.md`). This wave has the same shape: `packages/devtools/test/dockModelFixtures.ts` is shared by many files, and ~190 constructions change in Phase 79.
**Prevention:** keep any characterisation or contract file written by Phase 78 or 79 out of a shared helper that later phases edit, and keep fixtures that run code at load in their own module; at each phase close, re-run every earlier phase's record scripts (contract, agreement, mutation compare), not only `pnpm check:pr`; budget a re-verify of 77-79 at the milestone close and write the staleness script early (v1.7's `68-stale.mjs` pattern). Run `check:pr` with `< /dev/null` (gate 15's install prompt) and alone on a quiet host.
**Phase:** 78, 79, 80, and the close.

### Pitfall 17: Configure-only means the first `configure` is the real build; an empty build must be inert and the first configure must equal today's init
**What goes wrong:** several feeds do work in the build that `configure` currently skips on an unchanged input, so an empty build followed by a first `configure` is not the same as `build(init)`:
- `GatesFeed` build does `watch(registryNow); publish(readRegistry(), readAsked()); cadence()` (`GatesFeed.ts:~236-240`); its `configure` guards on `next.gates !== registryNow || watchFailure !== undefined` and `questions`/`intervalMillis` identity. An absent-to-absent first configure correctly does nothing, but `intervalMillis` absent -> present with `questions` unchanged restarts the cadence only through the guard; check each pair.
- `DiagnosticsFeed.configure(undefined)` as a **first** call runs `off()`: `runs.stop()`, a new store, `view.set(diagnosticsOff)`; with the build empty that is a wasted supersede and, with a throwing listener, a rethrow on a no-op. Today `init === undefined` skips it.
- `TimelineFeed` starts a read at build even with no source (`readSource(inputs.source)` -> `NO_SOURCE`, status `Reading`); the empty build should not start one, and the first `configure` with no source must still leave status `Reading` (not a new publish).
- `DockModel` computes `rail`, `shown`, `roles` and the `simulation` sightings from `inputs.catalogue` at build (`DockModel.ts:~187-206`), and the derived stores take their first `held` key from `inputs.reading` and `inputs.questions` at build. The first `configure` reaches them only through `spread()`, `roles.setList` and `shownReading.refresh()`; a missed one leaves a store on its empty key (the questions store would be stale until a parent notified).
- The ARCH-63 class: "an unchanged prop must not wipe a capture or a half-filled form" (`DockModel.ts` header). `makeSimulationSession(init?)` is amended by this wave (ADR-QD-137), and its first `setSightings`/`setPorts` after an empty build must not reseed a held choice or a run.
**Prevention:** a "first configure equals old init" table test per feed and for the model: build with init on the base (characterise status, snapshot identity, listener counts, forks started), then build empty plus `configure(init)` and compare. Make the empty build's snapshot the same constants (`diagnosticsOff`, `UNWATCHED`/`UNHANDED`, `READING`) so an unconfigured model keeps stable identity (`useSyncExternalStore`).
**Phase:** 79.

### Pitfall 18: A throwing listener during the first configure escapes through `useScoped`
**What goes wrong:** ADR-QD-177 rethrows what listeners threw after every listener ran. Today a build with `init` can only throw from the build; nobody is subscribed yet. If `configure` runs inside `useScoped`'s build, a throw inside the model's own subscriptions (the dock's `timeline.subscribe` -> `spread`) is caught by `useScoped`'s `try/catch`, which closes the scope and rethrows into the layout effect and the error boundary; run as a separate effect the same throw propagates from the effect instead, leaving a built model. Both are defensible, but the choice changes whether the model exists afterwards and must be pinned (`ExternalStore.test.ts`, `TimelineFeed.test.ts` hold the throw rows from Phase 64).
**Prevention:** decide, document and test "first configure throws" for the hook (scope closed vs model kept), and keep `try { push() } finally { start }` ordering inside every feed's `configure`.
**Phase:** 79.

### Pitfall 19: Mutating call order inside `DockModel.configure`
**What goes wrong:** `configure` order is load-bearing and commented: gates feed first ("re-reads the registry and the thunk before the shown reading is refreshed... publishes one join"), then diagnostics, then `shownReading.refresh()` (`DockModel.ts:~286-304`). A per-field rule table that dispatches "by feed" in table order, or in `Object.entries` order, can reorder them, and the join then publishes twice or reads a registry the host just handed away (Phase 56's finding). The derived stores subscribed to parents "in the order listed, when the store is built" (`ExternalStore.ts` doc).
**Prevention:** the rule decides *whether* a feed restarts; the dispatch order stays written once, in `configure`, and a test counts the questions store's publishes for a single `configure` that changes `gates`, `questions` and `reading` together (Phase 72's `heardOn` helper in `dockModelFixtures.ts`).
**Phase:** 79.

## Minor Pitfalls

### Pitfall 20: `Schema.brand` interaction with `decodeUnknown`/`encode`
**What goes wrong:** `brand` changes `Type` only; `Encoded` stays the unbranded struct, so `Schema.encode(AuditEntry)` accepts a branded value and a decode of the same schema yields it with no extra validation. A future caller reaching for `Schema.decodeUnknownResult(AuditEntry)` gets a branded value that skipped depth guard, strict options and `unwalked` (the exact thing section 7a of AGENTS.md exists to prevent). The house-style `[untrusted-decode]` budget counts such tokens in `packages/audit/src` and fails the gate.
**Prevention:** do not use `Schema.brand` on the codec's schema (Pitfall 1); no new `Schema.decode*` token outside the budgeted files; the codec stays `untrustedDecoder`-based.
**Phase:** 77.

### Pitfall 21: `ArchiveFacts` stops re-checking, but `SequenceNumberInvalid`/`EntryNotDecodable` are public tagged errors and a documented writer refusal
**What goes wrong:** `SequenceNumberInvalid` is exported via `SequenceIntegrity.ts` and cited by ADR-QD-110 and the audit README/website pages (`apps/website/src/content/docs/docs/packages/audit/capabilities.md`). Removing the write-path refusal removes a documented outcome: it must go through the changeset (Breaking), the upgrade guide, `spec/overview.md` (if the class is dropped from the barrel, gate 13 wants it removed from the table, and `check-package-install.mjs` probes names) and `features/features/wire-versions/wire-versions.steps.test.ts:163`, which calls `decodeAuditEntry` directly. Keep or remove deliberately; ADR-QD-110's amendment states which.
**Phase:** 77.

### Pitfall 22: `Effect.fn`/budget interactions in the new modules
**What goes wrong:** a new `LensSession` or `resize` implemented with `Effect.fnUntraced` or `switch` fails `UNTRACED_BUDGET` / `SWITCH_BUDGET`; use `Match.type<...>().pipe(Match.tagsExhaustive(...))` at module scope (AGENTS.md sections 5/5a). A module-level `let` for session state fails `MODULE_STATE_BUDGET` (`[module-state]`), and `Date.now`/`console`/`process.env` are refused. The lens session is a plain store (like `ExplorerSession.ts`), not an Effect service: do not wrap it in `Context.Service` just to match.
**Phase:** 80.

### Pitfall 23: Hand-wrapping and test-title hygiene recur in every review round
**What goes wrong:** over-width lines (v1.6 audit; 72 IN-01), titles that describe process or a phase, and comments citing plan ids (v1.5). `oxfmt` is not a gate (AGENTS.md section 17), so only review catches these, and each fix round forces a fresh mutation run (v1.6 inefficiency).
**Prevention:** fix wrap and wording **before** the post-review mutation re-close; keep titles to BEH/INV/ADR ids; never cite a D-number.
**Phase:** all.
