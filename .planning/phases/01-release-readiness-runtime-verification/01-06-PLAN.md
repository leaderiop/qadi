<objective>
Close UAT gap G-01-2: the `check (20.19.0)` merge-gate leg fails at its final
step because `apps/website` depends on Astro 7.2.9, whose own
`engines.node` is `>=22.12.0` — above the workspace's declared Node floor.

Every library gate passes on that leg. GitHub Actions run 33314894440 shows
typecheck, lint, circular, tstyche, the full 1850-test coverage suite, BDD
acceptance, all four spec gates, the packed-artifact install gate and all five
mutation runs green under a real Node 20.19.0, then `astro check` aborting with
*"Node.js v20.19.0 is not supported by Astro"*. The nine published packages are
compatible with the floor they declare. A private documentation app's build
toolchain is not, and never claimed to be.

**Approach, and why not the other two.** Downgrading Astro (option a) was
rejected on evidence: `@astrojs/starlight@0.41.7` peer-depends on
`astro: ^7.0.2`, so a Node-20-compatible Astro means downgrading Starlight, the
Starlight/Tailwind integration and the Tailwind Vite plugin with it — a rewrite
of the site's framework stack, which `PROJECT.md` puts outside this roadmap
("this roadmap touches only the site's production *deployment*, not its content
or design") and which `apps/website/PRODUCT.md` owns. Conditioning the workflow
per leg (option b, as literally described) was rejected because it breaks D-05
and AGENTS.md §15: `check.yml` would stop running `pnpm check` and nothing
else, and a second list of steps is a second definition of "done".

What this plan does instead is put the condition **inside the gate**, where it
is one command on both legs and a document gates its description: gate 22 reads
Astro's own `engines.node`, builds the site on every runtime that satisfies it,
and on a runtime below it prints one line saying so. A companion assertion in
the same script fails the build if *no* `check.yml` leg satisfies the floor, so
"the site is built somewhere" is checked rather than assumed.

D-07 is honored, not bent. It says fix a real incompatibility rather than lower
the floor or defer. The floor stays `>=20.19.0`, stays blocking (D-06), and no
library code changes — because there is no library incompatibility left to fix;
plan 01-05 fixed the one there was.

**On the requirement list.** COMPAT-01 is what this plan closes. REL-03 and
REL-04 are carried because their sign-off evidence lives in the same CI run:
merge gate 14 (`node scripts/check-package-install.mjs`) and the nine 0.3.0
manifests that plans 01-02 through 01-04 produced are currently only ever
verified inside a run that concludes `failure`. This plan adds no changeset, no
version change and no CHANGELOG edit — it makes the run those two requirements
cite conclude `success`.

**On not writing an ADR.** Considered and rejected as the wrong call: this is a
narrowing exception to "every gate runs on every leg" with a real, evidenced
alternative, which is exactly ADR-QD-034's shape (a measured exception to a
house rule). It gets ADR-QD-059. The purely additive website gates before it —
CCR-QD-090 (step 21) and CCR-QD-091 (step 22) — had no rejected alternative to
record and correctly got a Definitions of Done revision alone.

Purpose: make the floor leg conclude `success` end to end without weakening any
gate, and leave the narrowing checkable rather than remembered.
Output: one new gate script, one rewired root script, a Definitions of Done at
revision 1.6, ADR-QD-059 registered in both indexes, a corrected concerns entry,
and a two-leg CI run that is green on both legs.

    This is the vertical slice: the gate script, the root script that invokes
    it, and the document that gates that invocation — proven on two real Node
    runtimes before anything else is written.

    STEP 1 — write `scripts/check-website-build.mjs`.

    Open with a doc comment in house shape. Line one: it runs `apps/website`'s
    own check on every runtime whose Node satisfies the toolchain that app
    depends on. Then the why, in paragraphs: that Astro declares
    `engines.node` above the workspace's own floor; that the workspace floor is
    a claim about what the nine *published* packages support and this app is
    private and publishes nothing; that a skip which cannot be seen is the
    defect this repository keeps finding, so this one prints; and that reading
    the floor from Astro's manifest rather than restating it is what keeps this
    file correct after the next dependency bump. Cite ADR-QD-059 and
    CCR-QD-092.

    The script does five things, in this order. Every failure path exits
    non-zero with a message that names the file to edit — nothing here may fall
    back to a guess.

    1. **Resolve the floor.** Use `createRequire(import.meta.url)` and
       `require.resolve` for `astro/package.json` with `paths` set to the
       repository's `apps/website` directory (that specifier is in Astro's
       `exports` map — verified against the installed 7.2.9 — so this resolves
       through pnpm's store correctly). Read `engines.node` from it. A
       `MODULE_NOT_FOUND` means dependencies are not installed: say so, and say
       to run `pnpm install`. A missing `engines.node` means the skip condition
       has lost its source: say that, and say to read Astro's manifest and
       update this script deliberately.
    2. **Parse it, narrowly.** Accept only a bare `>=MAJOR.MINOR.PATCH` range —
       which is what Astro declares today. Anything else (a union, a caret, a
       range with an upper bound) exits non-zero saying this script understands
       only that one shape and that the parser must be widened deliberately
       rather than left to infer which runtimes a compound range admits. A
       silently mis-parsed range is a gate that runs or skips for a reason
       nobody chose.
    3. **Read the matrix.** Read `.github/workflows/check.yml` as text and pull
       the inline `node-version:` array out of it with a regular expression.
       Parse the workflow's text rather than adding a YAML dependency, for the
       reason `check-dod-table.mjs` gives for parsing markdown by line: the
       shape is fixed, and a dependency here would be a dependency inside the
       thing that decides whether the build passes. If that key is not found as
       an inline array, exit non-zero saying this gate can no longer tell which
       runtimes build the site and that the parse must be updated alongside the
       workflow.
    4. **Assert coverage.** Compare each declared leg against the floor,
       treating a bare major (`"26"`) as that major with zero minor and patch.
       If NO leg satisfies the floor, exit non-zero. This is the assertion that
       stops the carve-out decaying into an absence: the message must say that
       gate 22 would otherwise skip on every leg, and that either the matrix
       gains a satisfying runtime or the site's toolchain comes back down.
    5. **Build, or state the skip.** Compare `process.versions.node` to the
       floor.
       - Satisfied: print one line, then run `pnpm --filter @qadi/website check`
         from the repository root with `execFileSync` and `stdio: "inherit"`
         (`execFileSync` is the house pattern — `check-package-install.mjs`
         uses it five times). Propagate the child's exit status exactly; do not
         collapse a non-zero status to 1 and do not swallow it.
       - Not satisfied: print exactly ONE line and exit 0. That line names the
         running Node version, the floor and where it was read from, and the
         `check.yml` leg or legs that do build the site.

    Every line the script prints on its own behalf is prefixed `website-build: `
    — the convention `check-dod-table.mjs` and `check-website-doc-examples.mjs`
    already use. The sub-floor line contains the word `skipped`.

    Support one flag, `--explain`, which resolves the floor, reads the matrix,
    runs the coverage assertion, prints the floor with the manifest path it came
    from, prints each declared leg with whether it builds, prints a final line
    reading `verdict: build` or `verdict: skip` for the runtime currently
    executing — and exits 0 without invoking anything. It exists so both
    branches are inspectable from either runtime in seconds, which is the only
    way the sub-floor branch can be checked without a thirty-second build.

    STEP 2 — rewire. In the root `package.json`, change the `website` script's
    value to `node scripts/check-website-build.mjs`. Change nothing else: the
    `check` script string still ends `&& pnpm spec:website-examples && pnpm
    website`, so the step count and ordering are untouched, and `check.yml`
    still runs `pnpm check` and nothing else (D-05).

    STEP 3 — keep the documented gate and the real one in agreement. In
    `spec/process/definitions-of-done.md`, update ROW 22 of the merge-gate
    table only. Its Command cell becomes `node scripts/check-website-build.mjs`
    — `check-dod-table.mjs` strips backticks and compares that cell to the
    expanded script literally, so it must match character for character. Its
    Gate cell says what the gate now is: `apps/website` type-checks and builds
