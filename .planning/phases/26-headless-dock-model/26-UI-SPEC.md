# Phase 26 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This is a preserve contract.** Phase 26 (ARCH-74) is a structural refactor of `@qadi/devtools`' dock: one package-private, scoped `makeDockModel` replaces six React-built stores and their layout effects; one owned-model hook replaces the `useOwnedX` hooks; `Screen` takes the model instead of 18 props; the simulation and explorer sessions share one held-choice implementation (26-CONTEXT `<domain>`, D-01..D-09). **It changes no visual or copy decision.** Every token, spacing value, string, `data-testid`, aria attribute, the tab order and the DOM shape of `DevtoolsDock.tsx`, `Screen`, `RoleViewer.tsx`, `PolicyExplorer.tsx`, `Simulator.tsx` and the other panels must be byte-identical to the phase base. The pin is the existing DOM suite: 26-04 `must_haves` says every pre-existing `DevtoolsDock.test.tsx` case passes unchanged ("this plan edits no line of it", D-10), and 26-05 deletes only the 13 Model-class duplicates of rules the new `DockModel.test.ts` proves without rendering.

Phase 25's approved contract (`25-UI-SPEC.md`) stays in force in full: everything it froze for the Simulator is still frozen here, and this document does not restate it. Where a value is not repeated below, `25-UI-SPEC.md` is its source.

Sources: 26-CONTEXT.md (D-01..D-14, the DevtoolsDock.test.tsx inventory), 25-UI-SPEC.md and 25-UI-REVIEW.md (the preserve contract this continues; its rule 18 and warning 1), REQUIREMENTS.md DMOD-01..05, WX-01..06, and the code read directly at HEAD `784ee4cd` (Phase 25 executed): `packages/devtools/src/react/DevtoolsDock.tsx`, `RoleViewer.tsx`, `PolicyExplorer.tsx`, `Simulator.tsx`, `useScoped.ts`, `useDockSession.ts`, `useExplorerSession.ts`, `useTimeline.ts`, `theme.ts`, `model/HeldChoice.ts`, `model/SimulationSession.ts`, `model/ExplorerSession.ts`.

**Phase base.** 26-01 Task 1 records it in `.planning/phases/26-headless-dock-model/26-base.txt` (`git rev-parse --short HEAD` before the first 26-01 commit; `784ee4cd` when this contract was written). Every "byte-identical" below means identical to that commit. Nothing in this phase should edit `theme.ts` (sha1 at this writing `6673c73b0fa1cb2522ea54ee154c2e8de9084ef7`).

### Held choice: how each state renders today (the shared implementation must not change any of it)

`HeldChoice<A>` is `Empty | Listed{value,index} | Evicted{value}`. Three screens show one and they say three different things on purpose. D-08 and D-09 unify the **implementation** (one cell, no re-mapping) and must not unify the **words, elements or colours**. Each screen's own wording stays a literal in its own view or session menu; do not hoist it into the shared cell and do not "harmonise" log / list.

| State | Simulator policy select (`qadi-simulator-policy`, `aria-label="Policy"`) | Policy explorer (`PolicyExplorer.tsx`) | Role viewer (`RoleViewer.tsx`) |
|-------|---------------------------------------------------------------------------|----------------------------------------|--------------------------------|
| **Empty** (nothing listed, nothing held) | Whole screen is the `qadi-simulator-empty` paragraph (policy `None`). No select is rendered | Whole screen is the `qadi-policies-empty` paragraph, `padding: 16`, muted. No rail | Whole screen is the `qadi-roles-empty` paragraph, `padding: 16`, muted. No chips |
| **Listed** at position `i` (the head by default; first value shown is pinned, so a new head does not move it, INV-QD-107) | `select.value === String(i)`, option labelled by the sighting's `label`, no leading entry | Rail item `i` has `railItem(true)` (raised surface, `colors.text`); every other rail item `railItem(false)`. No evicted notice. Pane shows that sighting's tree or JSON | Chip `i` has `button(true)` (accent). Chip row is **omitted** when the list has exactly one role and it is not evicted; otherwise one `qadi-role-chip` per role, in list order, keyed by `role.name` |
| **Evicted** (the held value left the list; still a value in hand, still shown and still run) | **One leading option** `{label} — no longer in the log` (em dash U+2014), `value="evicted"`, selected (`select.value === "evicted"`); the rail's entries follow with values `String(index)` of the rail as it is now (so indices are not shifted by the leading entry). `choosePolicyAt` maps the position by subtracting that one leading entry; choosing the evicted entry itself is a no-op and notifies nobody | `qadi-policies-evicted` div above the toolbar, `muted`, `font.sizeSmall`, marginBottom 8: `{sighting.label} is no longer in the log` (**"log"**). **No** rail item is highlighted (`railIndex` is `undefined`; `Draft` also highlights none and shows no notice). The evicted policy's tree stays on screen | `qadi-role-evicted` paragraph, `muted`, `font.sizeSmall`: `{role.name} is no longer in the list` (**"list"**, not "log"). **Every** chip is `button(false)` (index `undefined`), and the chip row is shown even if only one role is listed. The evicted role's counts and tree stay on screen |
| **Seeded** (Simulator only, wins over the held choice) | One leading option `from the replayed row`, `value="seeded"`, selected; rail follows. While a row is seeded the held choice is **not** pinned (the conditional pin stays: `SimulationSession` calls `pin()` only while nothing is seeded) | not applicable | not applicable |
| **Draft** (explorer only: a pasted, loaded policy) | not applicable | Shown as the policy; no rail highlight; no evicted notice | not applicable |

Constants a shared cell must preserve, because each is visible:

- An evicted value resolves to **itself** (the value in hand), a listed value resolves to **the list's own element** (the newest object), so an explorer rail label or a tally stays current. First match wins on equal elements (`resolveHeld`).
- Pinning: the explorer pins the head on every `setSightings` (unconditional); the role viewer pins on `setList` and at construction; the Simulator pins only while no row is seeded. A user who has never chosen anything must see the same entry before and after a new decision arrives.
- Equality is per screen: policies by `sameSighting`, roles by `sameRole` (`a.name === b.name`). Two roles with the same name are one choice.
- A `choose` of what is already held, and a `setList` of the same elements, **publish nothing** (no re-render, no select flicker). Every effective command notifies exactly once (`ExplorerSession.test.ts:503`).

## Interaction Contract

What must hold across the refactor. All of it is observable in the DOM; the mechanism changes (one scoped model, one `configure` effect, one held-choice cell), the behaviour does not.

### Tabs, filters, selection

1. **Tab order and rendering.** Toolbar order: the `qadi` mark; seven tab buttons `Log`, `Inspector`, `Policies`, `Roles`, `Services`, `Simulator`, `React` (each `type="button"`, `aria-pressed` = active); `qadi-counts`; the `Filter decisions` input; the `All`-led environment segment; the `Any`-led verdict segment (`Allow`, `Deny`, `Error`, `Unknown`); `live` / `paused`; `clear view`. Then the body, which holds exactly one screen. Tab key order is DOM order. No tab is added, reordered or relabelled.
2. **A tab change touches nothing else** (INV-QD-107; model rule M9). Visiting every tab and returning leaves the log, the explorer's chosen policy, pasted draft and view, the role choice and the Simulator's form, capture and result exactly as they were. The explorer, role viewer and Simulator keep their choices across a tab round trip because the **dock model** owns them, not the screen.
3. **Filters and counts.** Counts are of the whole timeline and never narrow when the filter does; the environment options are exactly the environments present; a selection survives a filter that hides it; a selection dropped by capacity says the buffer moved on (existing wording in `Inspector`, untouched). All as `DockSession.test.ts` and the surviving DOM cases pin.
4. **Pause freezes every screen together.** Each new timeline the dock shows is the one pushed to the dock session, the explorer's rail and the Simulator's rail in that order, synchronously, before any listener runs (D-02). While `paused`, no screen changes; a record arriving while paused is not visible anywhere until resumed. `paused` / `live` toggles through the model's timeline; the button label, `aria-pressed` and style are as before.
5. **`clear view`** empties rows and counts in the dock and both rails and **keeps the tab** (M12). It never reaches back to a sink.
6. **Replay.** The Inspector's replay switches to the Simulator tab **and** seeds it with the row's policy and action, every time, including replaying the same row after another policy was chosen or after the form was edited (E8.1; M4-M7). A new record arriving after a replay keeps the seeded form and its edit and adds the new policy to the rail.
7. **A new head during a visit changes nothing visible.** While the reviewer is on a screen, a record that becomes the head neither moves the explorer's shown policy nor the Simulator's chosen policy (M8).
8. **Capacity change.** A new `capacity` empties the timeline and keeps the tab, the filters and every held choice, exactly as today (D-05, M11). The DOM shows fewer rows than the bound allows (existing case #25 moves to the model; the capacity-eviction wording case #43 stays in the DOM).

### Render timing (the rule Phase 25 added; this phase carries it from the simulation to the whole model)

9. **The dock renders nothing for one pass, then the whole dock.** `DevtoolsDock` renders `null` until `useDockModel`'s `useScoped` layout effect has built the model, then renders `DockFrame` once with every store already present. A layout-effect update lands before the browser paints, so no frame shows a partial dock (no toolbar without a body, no screen without its store); the server renders nothing. This is `25-UI-SPEC.md` rule 18 widened from "the session" to "the model" and is the only render-timing change. It must not become visible: do not render a skeleton, spinner, placeholder or fallback in that pass.
10. **`useScoped` clears its value on cleanup.** On cleanup it calls `setValue(undefined)` and closes the scope. A hidden `<Activity>` runs that cleanup, keeps its state and later runs the effect again, so without the clear a child that read the value once would keep the closed one. With it, the frame unmounts while hidden and the next model remounts every reader against a **live** one. Every reader of the model (`useDockSnapshot`, `useExplorerSnapshot`, `useHeldChoiceSnapshot`, `useSimulationSnapshot`) must therefore be mounted **only below** the `model !== undefined` branch and must read the model once; none may be called in the owner. The test that pins this today is `test/react/useSimulationSession.test.tsx` ("`<Activity>` ... `assert.notStrictEqual(owned, first)`", about l.135-165) and it names `useOwnedSimulationSession`, which this phase deletes: **that case is to be re-pointed at `useDockModel` (or `useScoped`) in the same change, not dropped.** `StrictMode`'s double mount is the same path: the first model's scope is closed and a fresh model built, safe because nothing was read or chosen in between.
11. **One scope per mounted dock** (D-13): closing it interrupts a simulation run in flight and a source read in flight (M13, M16). The visible effect is the one Phase 25 already has: after unmount nothing lands. There is no "closed" or "cancelled" message because nothing is on screen once the dock is gone.
12. **Source change, capacity change.** A new `source` or `capacity` re-reads into the buffer (D-14); the host prop is held by identity as before (`DevtoolsDockProps.source` doc, "build it at module scope or in a `useMemo`"). Unchanged host advice; no new copy.

### Focus, keyboard and accessibility (preserved, nothing added)

13. **No focus management is added or removed.** The dock moves focus nowhere on tab change, replay, clear, pause or when the model finishes building. A focused filter input keeps focus while the model publishes, because the inputs are controlled by snapshot values and the frame is not remounted by a publish (it remounts only through the Activity path in rule 10). The refactor must not cause a remount on a timeline publish, a held-choice command or a `configure` that changed nothing.
14. **Keyboard.** Everything is a native `<button>`, `<input>` or `<select>`; Tab order is DOM order (rule 1). The only custom key handler in the dock's screens is Enter in the Simulator's chip draft (`25-UI-SPEC.md` 15). No new shortcut, no new `onKeyDown`, no `autoFocus`.
15. **Accessibility attributes preserved.** `aria-label="Qadi devtools"` on the `<section>`; `aria-pressed` on every tab, `live`/`paused`, segment option and role chip (the `All` / `Any` reset buttons carry `button(value === undefined)` styling and **no** `aria-pressed` today, and keep that); `aria-label="Filter decisions"`; `aria-label="Policy"` on the select; the rest as in `25-UI-SPEC.md` 17.
16. **React state for decisions (AGENTS.md §13, DMOD-05).** The dock holds no decision in React state: `DevtoolsDock.tsx` and `useDockModel.ts` have no `useState`; the one `useState` that holds the model is `useScoped`'s. The dock reads no `@qadi/react` decision, so `outcomeOf` is not engaged and `DECISION_READ_BUDGET` stays unedited.

| overflow / long-text | long role names, policy labels, resource paths | 🧪 backstop | Existing layout (`flexWrap: wrap` chip row; `minWidth: 0` explorer pane; native select width); no truncation is added. Verified by the DOM suite plus a human visual check against a running dock |

**One assumption (not a visual change, recorded so it is a decision rather than a surprise).** Today the timeline's `paused` flag, its buffer and its source read live in the **owner** (`useTimeline`), so they survive a hidden `<Activity>`; the stores below the frame do not. After this phase the timeline is inside the model, whose scope `useScoped` closes on cleanup, so a hide/show cycle rebuilds the whole model: `paused` returns to `live` and the backlog is re-read from the source. This follows D-04 and D-13 (one scope per mounted dock) and D-05, and a host that never wraps the dock in `Activity` (the documented case) never sees it. Not a contract violation to fix here; if a human wants the timeline to survive a hidden `Activity`, that is a design change for a later phase, not something to add in 26-04. The executor records the behaviour in 26-04's SUMMARY.
