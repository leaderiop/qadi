<objective>
Make the signature ledger a keyed store, so the read rule that 11-01's fix depends on ("a resource-scoped query sees only
its own resource; a subject-wide one only subject-wide rows") is derived once instead of being every adapter's job. Today
each adapter implements `signaturesFor` itself (`packages/audit/src/SignatureLedger.ts:57-68`), so an adapter that matches
loosely (a prefix scan, a case-folded column, a missing `WHERE resource_id IS NULL`) over-grants exactly the way the
non-string-id defect did.

Ported from lost commit `8900b7e` (lost decision D-52-b, recommended option), with one premise that moved on `main`:
`signatureHistoryPort.key` (`packages/core/src/SignatureHistory.ts:261`) now keys the full request
`[subjectId, resourceId ?? null, meaning ?? null, signerRole ?? null]` (INV-QD-043). The lost plan's fixture grouped by the
full port key; on `main` that would split one pair by requirement and hide rows. So the fixture and the ledger use the
requirement-free projection, as `main`'s `SignatureLedgerTest.ts:45-55` already does. The ledger's own key
(`[1, subjectId, resourceId ?? null]`) is unaffected. This premise move is two-way (no published shape depends on it), so it
is not a checkpoint (D-02).

Release note for 11-07: `SignatureLedger`, `signatureHistoryFromLedger`, `ledgerEntryOf` and `SignatureLedgerTest` are
added by the still-pending `.changeset/signature-capture-keyed-by-question.md` (npm `@qadi/audit` latest is 0.11.0), so
the shape change amends that changeset in place rather than adding a Breaking entry (lost D-52-h, recommended).
</objective>
