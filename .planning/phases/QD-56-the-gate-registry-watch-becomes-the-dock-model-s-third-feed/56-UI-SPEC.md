# Phase QD-56 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This phase changes no pixel and no word, with one exception.** It is a model refactor of the
devtools Questions screen (`packages/devtools/src/react/QuestionsPanel.tsx` over
`packages/devtools/src/model/Gates.ts`' `joinQuestions`). CONTEXT.md D-09 pins every rendered state
byte-for-byte by a characterisation written on the phase base. The one exception is D-03: a
throwing `questions` thunk is now stated in the panel, where on the base it ended the whole
diagnostics poll. That one state is new and specified in full below. Every other value in this
document is a record of what exists, locked, and not a proposal.

Source of truth for existing values: `QuestionsPanel.tsx` and `packages/devtools/src/react/theme.ts`
on the phase base. Phase 55's contract (`55-UI-SPEC.md`) is the sibling for the Services tab and
shares `theme.ts`, `DiagnosticsNotice` and the `qadi-*-failed` precedent.

## Spacing Scale

Locked to what `QuestionsPanel.tsx` already uses. Not all values are multiples of 4, and that is
accepted: the contract is "unchanged" and normalising would change rendered output (D-09).

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px | `marginTop` of the hydration drops block |
| sm | 8px | `gap` of the question row; `marginTop` of the invalidate button |
| 6px | 6px | `marginBottom` of the pick-button wrapper |
| 10px | 10px | `marginTop` of the hydration block |
| 14px | 14px | `paddingLeft` of an instance row |

Exceptions: 6, 10 and 14 are existing, locked values. The new failure paragraph adds **no** spacing
of its own: it is a bare `<p>` with the same style object as `qadi-gates-failed`

failure paragraph takes. Do not add a margin to either one.

Touch targets: unchanged. The only interactive elements are the pick button, the highlight buttons
and the invalidate button; the new state adds none.

## Layout and Structure (locked)

Order inside `qadi-questions` (outer `div`, `diagnosticsRootProps(diagnostics.status)`), unchanged:

1. `DiagnosticsNotice` (shared, unchanged).
2. `qadi-keying-note`.
3. The **gates block**, one of: `qadi-gates-absent` (Absent), `qadi-gates-absent` carrying the Empty
   text (Empty), the pick button (Listed), `qadi-gates-failed` (Failed).
4. The **questions block**, one of: nothing (Unsampled), `qadi-questions-absent`,
   `qadi-questions-empty`, the question blocks (Rows), **`qadi-questions-failed` (new, Failed)**.
5. `qadi-hydration`.
6. `qadi-invalidate` button, only when `onInvalidate` is handed over.

**Where the new state renders (locked):** in slot 4, the questions block, as the sole content of
that block, directly after the gates block (slot 3) and directly before the hydration block (slot 5).
It does not render in the `DiagnosticsNotice`, in a new banner, in the gates block, or inside a
question row. It is a sibling `<p>` of the existing failure paragraph, not nested in it. It is not
in the dock toolbar and not on any other tab.

**Closed unions.** The questions view gains exactly one tag, so the union is
`Unsampled | Absent | Empty | Rows | Failed{reason}`. `QuestionsView.Failed` carries
`{ readonly reason: string }` as `GatesView.Failed` does. `GatesView` is unchanged
(`Absent | Empty | Listed | Failed`). The exact name is the researcher's recommendation under D-03's
discretion; if the planner picks a shared failure instead, every rule below still holds, since the
contract is the rendered element, not the tag. The `questionsBlock` matcher stays
`Match.tagsExhaustive`, so a missing arm is a compile error.

**It never claims rows.** `Failed` carries no rows. No `qadi-question-block`, no
`qadi-question` and no `qadi-highlight` renders for it, and the panel says nothing about what has or
has not been asked.

Interaction: unchanged. The new paragraph has no focus target, no hover or pressed state, no
keyboard behaviour and no motion. It carries no `role`, no `aria-live` and no `tabIndex`, as
`qadi-gates-failed` carries none.

## Copywriting Contract

### The new sentence (locked)

| Element | testid | Element / style | Copy |
|---------|--------|-----------------|------|
| Questions failed (new) | `qadi-questions-failed` | `<p>`, `style={{ ...muted, color: colors.error }}`, no other attribute | `The questions handed to the dock threw, so what has been asked cannot be shown: ` followed by `{reason}` |

- The wording is the sibling of the registry sentence, one clause for one clause: subject
  ("The registry" becomes "The questions"), the same verb phrase "handed to the dock threw", the
  same consequence frame "so ... cannot be shown", the same trailing colon-space and reason.
  "The questions" is the prop's own name (the absent note says "Pass `questions`").
- Neutral register: no "failed unexpectedly", no apology, no instruction beyond the reason, no
  emoji, no exclamation mark. The sentence ends in a colon, a space and the reason, with no full stop
  after the reason, as `qadi-gates-failed` does.
- `{reason}` is the same string the registry path prints: `Cause.pretty(Cause.die(thrown))`
  (`reasonOf`, moving into the feed under D-08), with the same fallback sentence
  `The registry threw a value that could not be described.` when the throw cannot be described.
  That fallback names "The registry" even for the thunk. **Decision: it is locked unchanged for the
  registry, and for the thunk the feed must use a fallback that names the questions, not the
  registry:** `The questions threw a value that could not be described.` A thunk's failure must not
  be reported as the registry's. (Flagged for the planner: `reasonOf` is shared today and takes the
  subject as a parameter or has a second fallback.)
- The reason is rendered raw after the sentence, in the same text node pattern as the sibling
  (`...cannot be shown: {reason}`), so a multi-line reason collapses its whitespace in the `<p>`
  exactly as the registry's does today. No `<pre>`, no truncation, no copy button.

## Failure rules (the contract the characterisation and the RED test pin)

These decide what the panel shows for each combination. "Registry" is the gates input, "thunk" the
`questions` input.

| Registry | Thunk | Gates block | Questions block | Rows' `asking` |
|----------|-------|-------------|-----------------|----------------|
| reads | reads, non-empty | per GatesView | Rows | per registry (list or "asked, nothing mounted") |
| reads | reads, empty | per GatesView | `qadi-questions-empty` | n/a |
| reads | not handed over, sampled | per GatesView | `qadi-questions-absent` | n/a |
| reads | not handed over, unsampled | per GatesView | nothing | n/a |
| fails | reads, non-empty | `qadi-gates-failed` | Rows | undefined (no claim; no `qadi-question-unmounted`, no highlight, no instances) |
| reads | **fails** | per GatesView (Listed shows the pick button if guards exist) | **`qadi-questions-failed`** | n/a, no rows |
| fails | **fails** | `qadi-gates-failed` | **`qadi-questions-failed`** | n/a, no rows |

- The two failures are independent. A throwing thunk does not turn the gates block into Failed or
  Absent, and a throwing registry does not turn the questions block into Failed. Both paragraphs
  render when both fail, gates first (slot 3), questions second (slot 4); neither suppresses nor
  merges with the other, and each states its own reason.
- A thunk failure does not blank the lens: guards the registry lists still reach the pick and
  highlight machinery (`snapshot.instances` is the registry's own list). With zero rows there is no
  highlight button to use, and the pick button still works.
- **Precedence inside the questions block** (view-level contract): questions present (supplied by the
  reading, or read from the thunk) wins, then the thunk failure, then unsampled, then absent. A
  failure is stated before "unsampled": like `qadi-gates-failed` and `qadi-wiring-failed` it renders
  regardless of whether the first sample has been taken, because it is a claim about a read that
  happened and not about an absence.
- **A supplied reading wins, unchanged.** A reading handed from elsewhere that carries its own
  `questions` takes precedence over what this process reads (CONTEXT.md D-02, `supplied.questions ??
  sampled.questions`). When the supplied reading carries questions, the panel shows those rows and the
  thunk's failure is not stated: nothing it would say is unread. When it does not, the thunk's
  failure is stated.
- **The poll keeps running.** On a throwing thunk the `DiagnosticsNotice` status is not `Stopped`;
  wiring, activity and calls on the Services tab keep updating. The RED test asserts `Live` (not
  `Stopped`) with the failure paragraph shown.
