Per D-10. Write `spec/decisions/191-a-timeline-store-owns-its-capacity.md`, titled `# ADR-QD-191 — A timeline store
owns its capacity`, Document ID `QADI-ADR-191`, Revision 1.0, Effective Date 2026-11-24, Status `Accepted — amends
ADR-QD-137`, Change History `1.0 (2026-11-24): Initial (ARCH-125, CCR-QD-470)`.

- **Context**: what the code before ADR-QD-191 did, from the evidence. The feed built a store per capacity, mirrored
  it into a second store through a listener and handed the host a forwarder, so the store a host held was not the
  store the read fed. `configure` assigned its inputs before the capacity was checked, so a refused capacity left the
  feed comparing with inputs it never took and a `restart` reading a source it never read. The capacity was compared by
  identity, so an omitted capacity and the default emptied a review and read it again. A zero-capacity timeline returned
  a new value per record, so a store notified and a feed re-rendered for records it kept nowhere. The hand-fed hook kept
  the capacity of its first render. `clear` rebuilt at the constructor's capacity. Name the RED tests by title.
- **Decision**, numbered: (1) the store's `resize(capacity): boolean`: checked first through `emptyTimeline`, the
  held capacity a no-op answering `false`, otherwise emptied at the new bound, released from a pause, published once,
  `true`; (2) the effective capacity is the store's, so a feed reads an omitted capacity as
  `DEFAULT_TIMELINE_CAPACITY`; (3) a record a zero-capacity timeline cannot keep returns the identical timeline,
  decided at `bound`; (4) a resize releases a pause, the held capacity keeps it, a refused one keeps it; (5) the feed
  holds one store for its life and returns it; (6) `configure` checks the capacity before it moves anything, and past
  the check reads again when the store resized or the source moved; (7) the idle store's `resize` answers `false`; (8)
  `useTimelineStore` resizes from a layout effect; (9) `clear` empties at the held capacity; (10) `publish`, not `set`,
  so the rule does not lean on the new value's identity. State the run-time guard: a missing or `null` capacity reads
  as the default, and any value that is not a non-negative integer is refused.
- **Alternatives considered**: keep the forwarder and fix its gaps (two stores stay, and every member forwarded is a
  member that can drift); replace the hand-fed store per capacity (`useMemo` keyed on it), which drops the store a host
  holds; compare capacities by identity; check only inside `resize` and catch in `configure` (the inputs would move
  first); a `setCapacity` returning nothing (the feed could not tell whether to read again); release the pause without
  publishing (a second subscription reading `isPaused` would miss it).
- **Consequences**: Breaking for `@qadi/devtools`, a minor release marked **Breaking**: `TimelineStore` gains a
  required `resize`, so an object a host writes as a `TimelineStore` needs one; moving between an omitted capacity
  and the default keeps the timeline and reads nothing again; a refused capacity throws from `configure` with the
  inputs unchanged; a zero-capacity view publishes nothing for records it cannot keep; `useTimelineStore` follows a
  changed `capacity`. Name the upgrade-guide section `0.13: a timeline store owns its capacity` and the changeset file
  `.changeset/devtools-timeline-store-owns-its-capacity.md`.
- **What enforces it**: the tests by file and title group (`TimelineStore.test.ts`'s `resizing` describe and the clear
  test, `TimelineFeed.test.ts` TF30 to TF36, `Timeline.test.ts`'s capacity tests, `useTimeline.test.tsx` UT4 and UT5,
  `surface.tst.ts`'s resize pins); the mutation floor of `Timeline.ts`, `TimelineStore.ts` and `TimelineFeed.ts`
  measured at the base through `stryker.devtools.mjs`; each new check seen failing once; `scripts/check-api-surface.mjs`
