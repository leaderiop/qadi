Conventions gathered at planning time:

- An ADR opens with a Document Control table (Document ID `QADI-ADR-NNN`, Revision, Effective Date, Status, Author "Qadi Engineering", Classification "Architecture Decision Record", Change History), then `---`, then `## Context`, `## Decision`, `## Alternatives considered`, `## Consequences` and `## Related`. - `spec/decisions/index.yaml` entries look like `- id: "ADR-QD-107"` / `file: "107-….md"` / `title: "…"` / `status: "Accepted — amends …"`.
- An amendment appends a `## Amendment (YYYY-MM-DD, ADR-QD-NNN, CCR-QD-NNN)` section to the amended ADR (094 has three such sections) and never rewrites earlier text, because change history is exempt from rewriting (AGENTS.md §15).
- Revision bumps are mechanical: run `node scripts/spec-revise.mjs <doc.md> "<what changed>"`. It bumps the minor version in both the Revision row and the Change History cell. Never hand-edit either. `node scripts/spec-revise.mjs --check` verifies every document.

ADR-QD-108/CCR-QD-385 are reserved for phase 1, and ADR-QD-109/CCR-QD-386 for this phase. Phases 2, 3, 4 and 6 may run in parallel, so re-run `next-id INV` at execution time and use what it prints. If a sibling phase claims the same INV id before merge, renumber on merge, because the README register is resolved the same way.

  - In four of the five ports, `spanAnswer` was just `disclose`.
  - Seven bodies repeated annotate, count, call, defect and annotate (six local reads plus `servedBody`).

Document Control: Document ID `QADI-ADR-109`, Revision 1.0, Effective Date today, Status "Accepted — amends ADR-QD-077, ADR-QD-094, ADR-QD-107, ADR-QD-058", Change History "1.0 (today): Initial (ARCH-47, CCR-QD-386)". Sections:

- Context: the verified facts in `<interfaces>`, as prose.
- Decision, as bullets:
  1. The projection lives on the description's span attributes: `pose(request)` for the question beside `disclose(answer, request)` for the answer (D-01). `PortWire` deals only with JSON, and `spanQuestion`/`spanAnswer`/`PortWireSpan` are removed.
  2. This is not a contradiction of ADR-QD-107. ADR-QD-107 refused span structs as the wire (lossy; INV-QD-044's floor). This decision moves the span projection off the wire and onto the span attributes, so the wire still never becomes a span and a span never becomes the wire (D-02, cite it explicitly).
  3. One read body: `readPort` in `PortAccess.ts`, a plain function that opens no span (D-06). It annotates the question, counts in the interpreter's sibling metric (evaluate, toPredicate or remote), invokes the port inside the effect `catchPortDefect` wraps, converts a defect, and annotates the answer (D-04). `servePortRead` is `readPort` with interpreter `"remote"` under the port's span. Each `ask*` keeps only argument shaping, `requireResourceId` with its annotate-before-validate order, the depth clamp and the signature match (D-05, D-07). The six span names and `UNTRACED_BUDGET` are unchanged.
  4. D-03's recorded choice. BEH-QD-227 promises `qadi.meaning`, `qadi.signer_role` and `qadi.matched` on `qadi.hasSignature`, and `@qadi/devtools` renders them, so the served span gains them; the local span keeps them. The asker's requirement crosses as optional `SignatureQuery.meaning`/`signerRole`: context, not a filter, and a store returns every signature on file whatever they say. The match rule is stated once (`signatureMatches`). `onFile` is recorded on neither span, because BEH-QD-227 does not list it and ARCH-21 kept a count off the span as a disclosure decision of its own. Name the inaccurate premise in PORT-04 plainly.
  5. Typing: the description's `attributes` is intersected with the two functions, typed by the description's request and answer, so a read generic over the port correlates without a cast. The structs are not intersected, so row types stay exact.
  6. Naming (Claude's discretion per CONTEXT): `pose`, because `question` is the struct and `questionOf` is `Question.ts`'s; and `readPort`.
- Alternatives considered:
  - The local span drops meaning/signer role/matched. Refused: spec and devtools.
  - The projection stays on the wire. Refused: two statements were the defect, and the wire is JSON.
  - `readPort` as `Effect.fn`. Refused: a second nested span per read. `Effect.fnUntraced` is refused for the budget.
  - Validate, then annotate only on failure. Refused: D-07's order. The cost is one agreeing extra annotation on the success path of the three resource-scoped reads.
  - The requirement as wire-only context. Impossible: `askRemotely`'s Shape sees only the port's request.
  - Recording `qadi.on_file`. Refused: the reason above.
- Consequences:
  - `SignatureQuery` gains two optional fields (additive).
  - The signature request key is now subject, resource, meaning and signer role (INV-QD-043's injectivity law). A devtools capture keys per requirement, so over-keying can only miss and deny.
  - Version skew: a new client against an old server is refused `Malformed` and becomes the port's typed error, failing closed.
  - `PortSpanAttributes.pose`, the two-argument `disclose` and the removals from `PortWire` affect only names added after `@qadi/core@0.11.0` and not yet released.
  - A served read whose store throws is now the port's typed error (`Unavailable` on the wire).
  - `PORT_DOUBLE_BUDGET` is unchanged.
- Related: ADR-QD-037 (the Port* leaf split stays), 051, 058, 077, 094, 107, BEH-QD-227, BEH-QD-332, INV-QD-N, INV-QD-043, INV-QD-044.

Write prose, not code fences. Any TypeScript in a spec doc uses a `ts` fence (not compiled) per AGENTS.md §12, and preferably none at all.
