<objective>
Pin the #64 follow-up gap at the new seam and close it (CACHE-03): an abandoned shared computation leaves the in-flight table in the same step that abandons it, so nobody can join it afterwards, and its eventual exit writes nothing and settles nobody.

Purpose: `awaitShared`'s doc comment lists three structural options (fall through to a fresh compute when a join lands on a claim with a pending interrupt; deliver the last-leaver signal as a typed abandon failure; or pin the regime). The first, done at the moment of abandonment rather than at the moment of joining, needs no new error type, changes no public type, and makes "a joiner never inherits an interrupt it did not receive" true by construction: a joiner can only reach a claim somebody is still waiting on.

Output: the fix in `SharedComputation.ts`, a seam-level RED-then-green test, 20-01's test green, bench after.
</objective>

- After 20-02: `SharedComputation.ts` holds `InFlightClaim<A, E> = { claim; fiber; waiters }`, `awaitShared` (onInterrupt: decrement, at 0 `Fiber.interrupt(entry.fiber)`), and `run` (one sync claim/join/hit step under `uninterruptibleMask`; compute forked detached with an `onExit` that calls the claim's settle, removes the `inFlight` entry if it is still this one, then `Deferred.done(claim, exit)`).
- Why removal by identity matters already: `onExit` only removes `inFlight[key]` if it is the same `InFlightClaim` object, so removing it earlier at abandonment and letting a fresh claim take the slot is already safe for that step.
- `Fiber.interrupt` awaits the target's exit. The last leaver therefore still waits for a compute parked uninterruptibly to finish, exactly as today; this plan does not change that (recorded as an observation in the SUMMARY, not in scope).
