<task type="checkpoint:decision" gate="blocking">
  <name>Task 1: how the role tree shows a role reached a second time (D-04, asked once)</name>
  <decision>When the devtools role tree reaches a role it has already shown (a diamond's second arm), does it walk that role's subtree again?</decision>
  <context>
Today it does, on purpose: "the shape is the catalogue's, and eliding it would show a reader a graph they do not have"
(`RoleTree.ts:84-86`). The cost is exponential in stacked diamonds: k = 10 / 16 / 20 → 4,093 / 262,141 / 4,194,301 nodes
(574 ms to build at k = 20, before any rendering). Nothing decides with the tree (`decidingSet` and the grants come from
core), so this is a display choice, not an authorization one. Either option fixes the name keying and the stack depth.
  </context>
  <options>
    <option id="A">
      <name>Recommended: a repeated role is a leaf that references its first occurrence</name>
      <pros>Node count = reachable roles + revisit edges (linear); every edge of the graph is still drawn; the reader can jump to the first occurrence to see the subtree; matches how `permissionProvenance` already resolves (first path wins)</pros>
      <cons>The repeated arm no longer shows its subtree inline; reverses the reasoning in the current comment, so a BEH and the comment change</cons>
    </option>
    <option id="B">
      <name>Keep re-walking repeated subtrees, with a linear cap</name>
      <pros>Small graphs look exactly as today</pros>
      <cons>Needs a cap (for example 4 × reachable roles) and a "truncated" marker once it is hit, so large graphs show an arbitrary prefix; a second rule to explain and test; the walk still re-traverses, so build time stays super-linear up to the cap</cons>
    </option>
  </options>
  <resume-signal>Answer "A" or "B" (B with a cap value if not 4 × roles).</resume-signal>
</task>
