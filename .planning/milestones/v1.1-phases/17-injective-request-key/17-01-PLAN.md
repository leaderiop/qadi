  <decision>For `AttributeResolver`, `RelationshipResolver`, `DecisionHistory` and `CustomPredicate`: when a Snapshot replay is asked a request the capture holds no answer for, does it answer the port's fail-closed `none` (today) or fail with the port's own typed error, as `SignatureHistory` already does?</decision>
  <context>
Why it matters. A replay miss answers `none` today. `none` denies an un-negated leaf, but `not(leaf)` then allows, so a what-if that wanders outside the captured set can report an allow that the real store would not give. That is the same fail-open an unwired real deployment has (INV-QD-007), and INV-QD-043 records it as known and not closed. `SignatureHistory`'s miss was flipped to an outage in v1.0 Phase 2 (WR-04) for this reason. Flipping each of the other four is a one-word change in `Capture.ts`'s `UNSEEN_REQUEST_IS_AN_OUTAGE`.

What A changes, stated honestly. A replay of a partial capture shows more errors. Every what-if edit that asks a question the Live run did not ask becomes an `Error` row (the port's typed error, "not captured") instead of a deny-or-allow row. That includes dropping a role from a subject that a custom predicate reads, a new attribute name, a different relationship depth, or a different history event. Six existing tests that pin today's answers change their expected outcome (listed in `<interfaces>`). A reviewer sweeping a Snapshot sees "this was not captured, run Live again" instead of a verdict the capture cannot back.

What B and C keep. B decides each port on its own reason (for example: an attribute miss is `undefined` exactly as the real store answers a missing attribute, so it could stay `none`). C keeps all four as they are and records the fail-open in INV-QD-043 and ADR-QD-129 as a deliberate choice.

Not affected by your choice: the key encoding work (plans 17-02 to 17-04) ships either way. A request whose arguments cannot be keyed at all (a cycle, a function, a class instance) always fails on replay, whatever you choose here, because there is no captured answer it could match. Plan 17-05 implements this answer with one test per port; plan 17-06 records it in ADR-QD-129.

Also confirm with the same reply (one line, no separate question): plan 17-03 changes `PortDescription.key` from `(args) => string` to `(args) => Result<string, KeyRefusal>` and makes `KeyRefusal`, `UnkeyableKind` and `describeKeyRefusal` public in `@qadi/core`. That is Breaking for anyone who wrote their own port description or called `.key` (a 0.x minor, with an upgrading note in 17-06). The alternative, a `key` that still returns a string and throws on a cycle, keeps today's stack overflow and collisions. Your A/B/C reply is taken as confirming it unless you add `key: object — <reason>`, which stops the phase before 17-03.
