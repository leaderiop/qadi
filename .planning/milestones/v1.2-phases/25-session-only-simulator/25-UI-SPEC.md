# Phase 25 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**This is a preserve contract.** Phase 25 (ARCH-73) is a refactor of `@qadi/devtools`' Simulator: the view becomes a pure view of one `SimulationSession`, and commands and readings move into the session (25-CONTEXT `<domain>`, D-03..D-05). **It changes no visual or copy decision.** Every token, spacing value, string, `data-testid`, aria attribute and DOM shape below is the current one and must be the same after the phase. The existing DOM tests (`test/react/Simulator.test.tsx`, `test/react/DevtoolsDock.test.tsx`) and the BDD suite are the pin (25-04 `must_haves`: "DOM test ids and visible texts are unchanged"). No new visual direction is introduced; nothing here is a new design decision, and every value is the existing codebase convention, cited file:line at the phase base (line numbers move as 25-03/25-04 edit the files; the strings and token values do not).

Sources: 25-CONTEXT.md (D-03, D-04, D-05, D-10..D-14, deferred list), 25-03-PLAN.md and 25-04-PLAN.md (surfaces that move), `_SHARED-CONTEXT.md` / `_WAVE7-CONTEXT.md` / `_DECISIONS-v1.2.md` (D-01, option D), AGENTS.md §13, and the code read directly: `packages/devtools/src/react/Simulator.tsx`, `theme.ts`, `VerdictTag.tsx`, `VerdictTreatment.ts`, `WhatIfTable.tsx`, `DevtoolsDock.tsx`, `model/SimulationSession.ts`, `model/SimulationSource.ts`.

## Interaction Contract

What must hold across the refactor. All of it is observable in the DOM and is pinned by tests; the mechanism changes (FiberHandle, scope, session commands), the behaviour does not. Where D-10/D-11 change an internal ordering, the visible effect is stated.

### Run, cancel, supersede

1. **A run is a click and a snapshot change.** `run` and `what if` call `session.run("Run"|"Sweep")` (a synchronous command, D-10). On a runnable policy the snapshot goes `Running` and both buttons disable in that same commit; the result area shows nothing until the run lands. Landing sets `Ran` (or `Broke`) once, and re-enables the buttons.
2. **Refusal is synchronous.** An unavailable source (`Snapshot` before a Live run, `Live` without `ports`) yields `Refused` at once: no `Running` flash, nothing evaluated, no fallback to Fixtures. The refused card names the chosen source and the reason.
3. **Superseding commands cancel the run in flight before they return.** `choosePolicy`/`choosePolicyAt`, `seed`/`replay`, `setPorts` while running, and a refused run all supersede (D-11). What the reviewer sees: the old run's result never appears (generation guard), and the screen returns to `Idle` (buttons enabled, no result card) for policy change, re-seed and ports change; a refused run shows `Refused`. A suspended Live run stops asking the application's resolvers when the command returns, with no host code and no reap.
4. **A new `run` supersedes the previous one.** Installing the new fiber interrupts the old at once. Only the latest run can land; the old run's exit is never applied. Run and what-if are disabled while `Running`, so a click cannot double-start; a command-started supersede is the path that matters.
5. **Closing the scope ends the run.** Unmounting the dock closes the session's scope, which interrupts a run in flight; a run that the close interrupts can never land, and `run` on a closed session does nothing (D-09). Unmounting the Simulator view alone no longer stops a run (the dock owns the session, so a tab switch keeps the form, the Live capture and the result); there is no "closed run" message because nothing is on screen once the dock is gone.
6. **Tab switch.** Leaving and re-entering the Simulator tab shows the same form, capture and result (INV-QD-107). This was `DevtoolsDock`'s ownership and stays so (D-14).
7. **A superseded run shows nothing of itself.** There is no "cancelled" state or copy. After supersede the state is `Idle` (or `Refused` for a refused run). No toast, no message.
8. **Stale, not cleared.** Editing the form after a run keeps the `Ran` card and adds the amber `stale` marker (E7.4); the result is never presented as current. Only policy change, re-seed and a ports change while running clear it to `Idle` (D-11 / `reseed`, `choosePolicy`, `setPorts`).
9. **Switching source does not clear the result** (it changes where the next answers come from, `SimulationSession.ts` `chooseSource`). `setPorts` clears the Live capture, so `Snapshot` becomes unavailable again with its reason.

### Inputs and the commands that replaced view logic

10. **Policy select** dispatches `session.choosePolicyAt(event.target.selectedIndex)` (D-03). The view renders `policyMenu.options` in order and parses no value. The selected option is `policyMenu.selected`. Choosing the already-selected entry, the seeded or evicted entry (index 0 while present), a non-integer, or an out-of-range position is a no-op and notifies nobody; the dropdown must not flicker or reset.
11. **Action input** dispatches `session.setAction(event.target.value)`. An empty string removes the action (absent, not empty: `hasAction` fails with `MissingAction` otherwise). Typing is controlled by `draft.action ?? ""`, so deleting the last character leaves an empty field, not the string `undefined`. Same no-op rule as `edit`.
12. **Resource, subject id, chips, clock, pairs, source** keep their existing commands (`editResourceText`, `renameSubject`, `addChip`, `removeChip`, `setClock`, `setPairs`, `chooseSource`). Unchanged.
13. **The chip typing buffer is the only React state in the view** (`useState` in `FieldEditor`, `Simulator.tsx:683`; `WhatIfTable`'s `only what changed` toggle is its own). No decision, run state or reading is held in React state (AGENTS.md §13). Nothing here calls `readOutcome`, `matchesBaseline`, `summarise`, `actionOf`, `withAction` or `/^\d+$/` after 25-04.

### Focus and keyboard (preserved, nothing added)

14. **No focus management is added or removed.** The Simulator does not move focus on run, on result, on refusal or on supersede, and does not auto-focus any control (none exists today). A focused input keeps focus while the session commits, because inputs are controlled by snapshot values and keyed stably; the refactor must not remount the form (the same `SimulatorView` instance renders for the lifetime of the session).
15. **Keyboard.** Everything is a native `<button>`, `<input>` or `<select>`, so Tab order is DOM order: policy select, source buttons, clock buttons, `pairs`, `run`, `what if`, then the cards top to bottom. The one custom key handler is **Enter in a chip draft commits it** (`Simulator.tsx:633-635`); a refused value keeps its text and shows its error. The dock's own keys are untouched. There are no new shortcuts. `Escape` does not cancel a run, and nothing should be added.
16. **Disabled-while-running.** `run`/`what if` use the native `disabled` attribute during `Running`, so a keyboard user focused on `run` loses focus to the document when it disables; this is existing behaviour and is not "fixed" here.
17. **Accessibility attributes preserved:** `aria-label="Policy"`, `aria-pressed` on every toggle (source, clock, pairs, tab buttons, `only what changed`), `<label htmlFor>` for `qadi-subject-id`, `qadi-action`, `qadi-resource`, `aria-label="Add {label}"` on chip drafts, `aria-label="Remove {label}"` on chip removes, `title` on source buttons carrying the reason.
18. **StrictMode / first render (D-13, new but invisible):** the owning hook renders `null` for one pass until its layout effect builds the session. A layout-effect update lands before paint, so no frame shows the dock or Simulator without a session; the server renders nothing. This is the only render-timing change and it is not visible to the user.

## Executor Guardrails

- Do not change any value in `theme.ts`, any inline style in `Simulator.tsx`, or any rendered string, `data-testid` or aria attribute. A diff that touches them is a defect unless it is a pure relocation of a string into the model with byte-identical text.

- Do not move or duplicate "This is not a denial" (Phase 29) or `Duration`'s clock sentence (deferred).
- Visual verification beyond the DOM tests is a human check against the running dock, not an automated gate.
