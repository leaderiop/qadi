<objective>
Write `addGuardedRoute` once, in `GuardRoute.ts`, absorbing `guardRoute`; state the route-method union once; leave
`PermissionRegistry.ts` holding the registry only and move the two `/__permissions` constructors to
`PermissionRegistryRoute.ts`. Then delete `guardRoute` and the tests that targeted it.

Purpose: ROUTE-01..03 (ARCH-75). `guardRoute` was a one-caller reshape whose doc comment and type tests guarded the wrong
function; `PermissionRegistry.ts` mixed the registry with the route builder; the method union was written twice. The two
deviations from the requirements' wording (unguarded routes stay a private sibling; `/__permissions` leaves the registry
module) are forced by the barrel and the cycle gate and are explained in 27-CONTEXT.md.

Output: one rewritten module, one new module, one slimmed module, re-pointed imports, deleted shim and tests, the comments and
overview rows that named `guardRoute` corrected. No public name, type, path, status or log line changes.

Shape: three tasks so the logic, the mechanical re-pointing and the wording sweep are each verified on their own. Task 1 is the
logic in five files (the four modules and the barrel). Task 2 re-points every importer and deletes the shim's tests; it shares
Task 1's commit because the tree does not typecheck between them. Task 3 is the comment and overview sweep, a separate commit
gated to change comment lines only. The file count (20) is the floor for this change, not scope creep. Every importer must move
in the same commit as the export it imports. A re-export left in `PermissionRegistry.ts` would close the
`GuardRoute.ts` ↔ `PermissionRegistry.ts` cycle this phase exists to avoid. Of the 20 entries, six carry real edits (the four
modules, `GuardRoute.tst.ts` and the deleted `PermissionRegistry.tst.ts`). The other 14 are import lines, barrel lines, comment
wording or overview table cells.
