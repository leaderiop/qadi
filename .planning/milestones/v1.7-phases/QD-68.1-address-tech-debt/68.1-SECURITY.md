## AR-68.1-01 re-measured (2026-11-22, after the milestone)

The accepted risk was re-measured instead of carried. A probe child (a copy of the gate's child shape, placed beside it in
`scripts/lib/` only for the run so `typescript/unstable/sync` resolves, then removed) opened a one-file project with the
`API`, wrote the process ids of its own children (`pgrep -P <child pid>`) to stderr, and spun forever. The parent ran it
with `execFileSync(process.execPath, …, { stdio: "pipe", timeout: 8000 })`, as the gate does with `CHILD_TIMEOUT_MS`.

| Observation | Result |
|-------------|--------|
| The child | killed at the timeout: `ETIMEDOUT`, `SIGTERM` |
| The server the `API` started (one process, pid 50458, a direct child of the gate's child) | gone when checked by its pid at once, and three seconds later |
| How it ends | typescript@7.0.2's `syncChannel.js` talks to the server over the child's stdin/stdout pipes; its own cleanup is a `process.on("exit")` hook that a signal kill skips, so the server ends because its input pipe closes |
| `spawnSync` with `detached: true` | supported on Node 26.13 (the child became its own process-group leader) |

**Disposition, narrowed.** A server that still reads its input exits with its child, so the recorded residue ("may
outlive the run") does not hold in general. What remains is a server stuck in a computation that never reads its input
again. Running the child detached and killing its process group would end that case too, but a Ctrl-C at the terminal
reaches only the foreground group, so the child and its server would then survive an interrupted gate: a more common
case traded for a rarer one. The gate keeps its child in the foreground group. ADR-QD-033 Rev 1.7, the
`CHILD_TIMEOUT_MS` comment and the CCR-QD-460 row now say this. AR-68.1-01 stays accepted, for the narrower case.

## AR-68.1-01 closed (2026-11-22, after the fourth review)

> The section above measured an idle server: its probe child spun after its request had returned, so the server was
> waiting on its pipe and saw it close. The fourth review pass showed that this is the case the gate's child cannot reach.
> Every point where that child can block is a server request, so at the timeout the server is mid-request and does not
> read its pipe. "Does not hold in general" was wrong, and the narrowing it made is withdrawn.

| Run (replica of the gate's call, `execFileSync(..., { stdio: "pipe", timeout: 1500 })`, a 1,500-file project, typescript@7.0.2) | Servers left at +0 ms | at +1.5 s |
|---|---|---|
| Before `b45e798a` (the child killed inside `updateSnapshot`) | 1, re-parented to pid 1, at 668% then 440% CPU | 1 |
| After `b45e798a` (the child wrote `server pids: 72533`; the gate killed it) | 0 | 0 |
| After, with no timeout (the parse ran to completion, ~6.5–15 s on a loaded host) | 0 | 0 |

**Mitigation.** Once the `API` has started its server, the child writes `server pids: <pid>` to stderr (`pgrep -P`, under
a 10 s timeout; without `pgrep` it names nothing and the old residue returns). When the child dies by a signal, the gate
kills each pid it named. A child that exits on its own has run `api.close()`, so the gate kills nothing and no reused pid
can be hit. The child stays in the terminal's process group, so a Ctrl-C still reaches the child and its server (the
reason a detached child with a group kill was not used). ADR-QD-033 Rev 1.8, the `CHILD_TIMEOUT_MS` comment, the child's
header and the CCR-QD-460 row say this.

**Disposition.** T-68.1-15 moves from accept to mitigate. AR-68.1-01 is closed, and the phase has no accepted risk left.
Residue: a host without `pgrep` (it ships with macOS and procps on Linux).
