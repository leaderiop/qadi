## Warnings

### WR-01: `// @effect-diagnostics ...` is not read as an instruction, and this repo has one in a compared file

**File:** `.planning/phases/QD-68.1-address-tech-debt/68.1-compare.mjs:104-118`
**Issue:** `DIRECTIVE` has no alternative for the Effect language service's `@effect-diagnostics` and `@effect-diagnostics-next-line` comments. I planted each of these, and each reads `same`:

- Deleting `// @effect-diagnostics effect/floatingEffect:error` from a file.
- Deleting `// @effect-diagnostics-next-line effect/floatingEffect:off` from above a statement.

This repo uses exactly that comment, at `packages/core/test/FloatingEffectPins.tst.ts:77`. AGENTS.md section 6 describes the block it opens ("one that turns the rule on with an in-file directive and runs in both passes") as load-bearing for `[not-callable-control]`. Deleting it changes the type-check result of every pin in the block under it, and that file is one of the ten Phase 68 verdicts the script re-checks. The header does name `@tstyche`, the other directive in that file, so a reader will assume the file's instructions are covered. The generic "any other tool's directive" residual does not tell them this one is not. The recorded verdicts still hold (see Summary), so this is a gap for the next comparison, not a wrong recorded answer.

**Fix:** Add one alternative, and the `-next-line` form pairs with the next line of code through the existing `NEXT_LINE` regex:
```js
String.raw`@effect-diagnostics[\w-]*\b[^\r\n*]*`,
```
Add two self-test cases (a deleted `@effect-diagnostics`, a deleted `@effect-diagnostics-next-line`), add a reflow case for the `-next-line` form next to the `@ts-expect-error` ones, and name `@effect-diagnostics` in the header's list.

## Info

### IN-01: `probe-guard-parse.mjs` has failure paths its header and the parent do not cover

**File:** `scripts/lib/probe-guard-parse.mjs:19-20`, `scripts/lib/probe-guard-parse.mjs:86-87`
**Issue:** Unchanged. `JSON.parse(probes)` and `new Map(...)` run outside the `try`, and `String(error.message)` prints `undefined` for a non-`Error` throw. In the parent, a non-JSON stdout line makes `JSON.parse` throw a `SyntaxError` that drops the child's output.
**Fix:** Move the argument parsing into the `try`; write `String(error?.message ?? error)`; wrap the parent's `JSON.parse` so a failure includes the child's stdout.

### IN-06: Importing the module runs `main()`, and a wrong working directory gives a raw `ENOENT`

**File:** `.planning/phases/QD-68.1-address-tech-debt/68.1-compare.mjs:50-56`, `.planning/phases/QD-68.1-address-tech-debt/68.1-compare.mjs:381-382`
**Issue:** The file exports `masked`, `jsxText`, `entries` and `differs`, but importing it runs `main()`, which exits 2 with usage unless `process.argv[2]` is set first. The exports cannot be used without that workaround. Separately, `readdirSync("node_modules/.pnpm")` runs at load time, so running the script from any directory but the repository root dies with a bare `ENOENT` stack and no message that says "run from the repository root".
**Fix:** Drop the `export`s (nothing imports them), or guard `main` with an `import.meta.url` check. Catch the `readdirSync` failure and throw "run from the repository root".
