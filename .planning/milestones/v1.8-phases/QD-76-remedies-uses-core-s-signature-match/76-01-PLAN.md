## ADR-QD-189 at Rev 1.0

File `spec/decisions/189-remedies-asks-core-whether-a-fixture-row-meets-a-signature-or-acted-leaf.md`, title
`# ADR-QD-189 — Remedies asks core whether a fixture row meets a signature or acted leaf`, Document Control copied from
ADR-QD-188's shape: Document ID `QADI-ADR-189`, Revision `1.0`, Effective Date `2026-11-23`, Status `Accepted — amends
ADR-QD-058 and ADR-QD-094`, Change History `1.0 (2026-11-23): Initial release (ARCH-123, CCR-QD-468)`. Sections, in
prose, numbered decisions, no decision number of the plan:

1. `## Context` — what the code before ADR-QD-189 did: the remedy table's `Signature` arm restated the signature port's
   match and scoping inline (the subject, a resource id exactly when the leaf is resource-scoped, the meaning, the
   signer role when the leaf names one); its `Acted` arm read both scopes as the exact `(subject, event, resource)`
   triple, so at `Any` scope it offered a redundant event row for a subject that had acted on another resource and
   called a leaf that already holds unremediable at a site with no resource id (BEH-QD-092); a signature fixture the
   port refuses (an untyped row whose subject has no request key) was read as unmet and offered a row that still fails;
   a request the signature key refuses because its subject id is not a string (a symbol) made the port read die, since
   `signatureHistoryPort.failure` built `SignatureHistoryUnavailable` with that subject id and the error's schema
   refused it, against BEH-QD-410's rule that a refused key fails closed and never throws; the history fixture keyed
   its rows by structural hashing, so a row or request member whose read throws (a revoked proxy) threw out of the
   fixture, and a member no key admits (a symbol) answered `"NotActed"`, which `hasNotActed` reads as an allow; and the
   custom-predicate refusal was two sentences for one fact, one in the remedy table and one in the simulation
   field table. Devtools already asks core's `judgeMatcher` for matcher leaves (ADR-QD-091), and core already writes the
   fixture data-to-layer mapping once (`PORT_FIXTURES`).
2. `## Decision` — numbered: (1) a change, not a recorded rejection: whether a fixture row meets a `hasSignature` or
   `hasActed` leaf is core's answer, and `SignatureMatch.ts` stays package-private; decided autonomously under the
   owner's standing instruction ("do not ask me; always pick the most complete and clean solutions") in place of the
   roadmap's owner question, and recorded before any source change; (2) core gains two pure, synchronous judgements on
   its fixture side: `signatureAnswerFromSignatures(signatures, leaf, site)` beside `signatureHistoryFromSignatures`,
   answering `Result<SignatureAnswer, MissingResourceId | SignatureHistoryUnavailable>`, and
   `actedAnswerFromEvents(events, leaf, site)` beside `decisionHistoryFromEvents`, answering `Result<"Acted" |
   "NotActed", MissingResourceId | DecisionHistoryUnavailable>`; each answers what its port, read for that leaf at that
   site over those rows, answers, in the read's order (the description's `asks`, the missing-id check, the lookup); the
   acted judgement carries no `"Unknown"`, because the closed-world event fixture never answers it, and each judgement
   carries its port's unavailable error, because a row or request the key refuses reaches it; (3) each fixture's lookup
   is module-private and read by both its layer and its judgement, and the answer `{ matched, onFile }` is built by one
   rule in `SignatureMatch.ts` that `askSignature` and the signature judgement share; the history fixture keys its rows
   and its requests through `decisionHistoryPort.key`, as the signature fixture keys through `signatureHistoryPort.key`,
   so both fixtures read one key text per pair and fail closed on one refusal (BEH-QD-410); (4) the refusal is total:
   for every value a request member or a fixture row field holds, the port read, the fixture layer and the judgement
   answer or fail with the port's own typed error and never throw or die; `SignatureHistoryUnavailable.subjectId` and
   `DecisionHistoryUnavailable.event` become optional, and each description's `failure` sets a member only when the
   member's own schema admits the request's value (`Schema.is`), as it already did for `resourceId`, so an absent member
   says the request held a value the wire cannot carry and the cause carries `describeKeyRefusal`'s sentence, which
   names it; the representation is the error class itself, so `SinkCodec` and `@qadi/http`'s response body carry an
   absent member with no second schema (ADR-QD-060), and the response body's two members become optional with it; a
   record whose own property read throws is outside the domain, as for every reader of a plain record; (5) the remedy
   table asks: the site is `subjectOf`'s subject and the form's resource; for a signature, met is
   no row, unmet is one `AddSignature` row whose resource id is the request's (from the description's `asks`),
   `MissingResourceId` is skipped with "the check names no resource id" and `SignatureHistoryUnavailable` is skipped
   with the refusal's text; for an event, `Acted` is no row, `NotActed` with a site resource id is one `AddEvent` row
