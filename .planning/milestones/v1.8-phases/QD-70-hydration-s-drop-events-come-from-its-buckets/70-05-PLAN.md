   - Context: on the hydrate side the engine kept three named arrays and a record pointing at them, pushed the

   - Decision, numbered: (1) each side's drops are collected in one record keyed by every drop reason of the side,
     built per call by a total constructor in the package-private `packages/react/src/HydrationBuckets.ts`
     (`entryBuckets`, `dehydrationBuckets`, typed by `DropBuckets`); no named per-reason array remains, and the entry
     whose fields disagree with its policy goes through the `MalformedEntry` key; (2) one generic function, `dropEvents`,
     derives each side's events from its record, one event per non-empty bucket in the record's key order, and the
     planner appends `Seeded` or `Dehydrated`; (3) the constructors' key order is the emission order, stated once per
     side and the base's: `EntryTooDeep`, `MalformedEntry`, `UndecodablePolicy`, then `ForeignSubject`,
     `UnencodablePolicy`; not read off core's table, whose entry order differs, because the events must stay
     byte-identical; (4) the payload path is folded in: `PAYLOAD_PRODUCERS` in `HydrationEngine.ts` names, for every
     whole-payload reason, what raises it (one of the payload decoder's refusals by tag, or the subject check), and the
     refusal-to-reason direction, `PAYLOAD_REASONS`, is typed against it, so a producer named by two rows or by none
     does not compile and a new decoder refusal is TS2741; a refused payload is still one `PayloadRefused` event, and
     the path has no buckets, because its refusal is exclusive; (5) the dehydrate side still runs the subject check
     first, so an entry both foreign and unencodable is `ForeignSubject` and is never encoded; (6) why ADR-QD-152's
     reason no longer applies, exactly as the interfaces state it, naming ARCH-118 and its two call sites.
   - Alternatives considered: leaving the payload path as it was (one of three kinds could still gain a reason nothing
     produces); the payload path in buckets with one non-empty bucket (misstates an exclusive refusal as a partition);
     the order read off core's table (changes what a reporter sees first); a checked tuple for the order (the record's
     key order states it already, a missing key being TS2741 and a duplicate TS1117, so a tuple would be a second
     statement of it); one derivation per side (two copies of one rule); `PAYLOAD_PRODUCERS` in `HydrationBuckets.ts`
     (it maps the payload decoder's refusals, which sit beside it in the engine, and a reader of the payload path meets
     it there); exporting the module ([ADR-QD-099](./099-entry-points-are-a-closed-list.md): out of the barrel is
