## RED ordering decision (orchestrator note answered)

The races are written against the base's existing `claim` hook, so they compile and fail on the "superseded exit is never
settled" assertion, as recommended. **The harness migration to `settle` is not in the `standing` commit**, though; it is
31-03 Task 1, after the deletion. Why: `settle(key, exit)` has no claim-time step, so `DecisionCache`'s claim-time
counter read cannot survive it. Migrating in the `standing` commit would force the counter's deletion into that commit and
collapse D-09's "deleted in its own commit". The order is therefore: RED (this plan) → `standing`, hook unchanged (31-02
Task 1, the races turn green with no test edit) → the counter deleted, `DecisionCache.ts` only (31-02 Task 2) → the hook
becomes `settle` everywhere (31-03 Task 1), which is D-05's own premise: with no claim-time read left in any adapter, a hook
that returns a closure has no purpose.
