# Phase 34 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.

**Scope.** One visible change: every dock screen that renders from the merged diagnostics reading
states the diagnostics feed's status (CONTEXT D-02, D-04, D-06, D-07), through **one shared notice**.
`DevtoolsDock.tsx`'s `Screen` hands `shown` (the merged `Diagnostics`) to exactly two screens, and
`shown` is read nowhere else:

| Screen (tab) | File | Fields it reads from the reading |
|--------------|------|----------------------------------|
| Services (`services`) | `packages/devtools/src/react/ServicesPanel.tsx` | `wiring`, `activity`, `portCalls` |
| Questions (`questions`) | `packages/devtools/src/react/QuestionsPanel.tsx` | `questions`, `hydration` (the hydration block is a section of this screen, not a tab of its own) |

The other five screens (`log`, `inspector`, `policies`, `roles`, `simulator`) read the model's other
stores and the host props, never `shown`, so they take no notice. Re-check at implementation: any
screen added to `Screen` later that reads `shown` must render the notice (the same rule).

Every token below is an existing token from `packages/devtools/src/react/theme.ts`; **no new colour,
font, size or weight is added.**

## Layout and Structure

### The shared notice: `DiagnosticsNotice`

One package-private component, one file: **`packages/devtools/src/react/DiagnosticsNotice.tsx`**. It is
not exported from `packages/devtools/src/react/index.ts` (the named barrel; ADR-QD-099: out of the barrel
is not importable) and needs no row in the overview's export tables. The same file holds the one
package-private helper `diagnosticsRootProps` (below). Neither Services nor Questions writes its own
notice markup, copy or styles; each renders `<DiagnosticsNotice {...diagnostics} />` as the **first
child of its root element**, above all other content.

```
<screen root> (padding 12, tabIndex -1, no outline override, data-diagnostics-status="<Off|Starting|Live|Stopped>")
  <DiagnosticsNotice />
    qadi-diagnostics-region                 role="status", always rendered, empty unless Starting
      [Starting]  qadi-diagnostics-starting   the Starting box (no role of its own)
    [Stopped]   qadi-diagnostics-notice     the amber box, keyed per stop
                  qadi-diagnostics-stopped    role="alert" the first time this stop is shown, none after
                                              (holds the lead + body only)
                  qadi-diagnostics-reason     <pre>, only when reason is non-empty, OUTSIDE the alert
                  qadi-diagnostics-restart    <button type="button">
  ...the screen's own content, as today (see "Suppressed copy" for the exceptions)
```

### Props: one `diagnostics` binding

Both `ServicesPanel` and `QuestionsPanel` gain **one required prop**, `diagnostics:
DiagnosticsNoticeProps` (the panels decide nothing; `DockFrame` builds it once):

| Field | Type | Meaning |
|-------|------|---------|
| `status` | `DiagnosticsStatus` | The diagnostics store snapshot's closed status (`Off`, `Starting`, `Live`, `Stopped { reason, sampled }`), read once in `DockFrame` |
| `onRestart` | `() => void` | The feed's `restart()`, as the dock model exposes it |
| `announced` | `RefObject<StopLedger>` | `DockFrame`'s record of the last stop a notice showed and how many distinct stops there have been (see Accessibility) |

Dispatch on `status` uses `Match.type<DiagnosticsStatus>().pipe(Match.tagsExhaustive(...))`, built once
at module scope, in the same shape as `wiringView` (AGENTS.md §5a). `DockFrame` holds the `announced`
ref (it outlives every screen, which is what makes "once per stop" possible) and builds the binding in
`useMemo` so the panels receive a stable object.

### Screen root helper

`diagnosticsRootProps(status)` returns `{ "data-diagnostics-status": status._tag, tabIndex: -1, style: {
padding: 12 } }`, spread onto each screen's existing root `<div>` (`qadi-services`,
`qadi-questions`) beside its own `data-testid`. `tabIndex -1` makes the root a programmatic focus target
for the restart handler, not a tab stop. It sets **no `outline`**: the dock has no focus token of its own
(its buttons use the browser default), so the root keeps the browser's focus ring, and a keyboard user who
restarts sees where focus went. One helper means the two screens cannot drift.

### State table (identical on every screen)

| Status | Notice | Reading shown beneath | `data-diagnostics-status` |
|--------|--------|-----------------------|---------------------------|
| `Off` | none | as today (no diagnostics handed over); every existing "not handed" message stays | `Off` |
| `Starting` | Starting notice | the store's reading (the `noDiagnostics` constant, or a supplied `reading`'s fields), with the suppressions below | `Starting` |
| `Live` | none | as today | `Live` |
| `Stopped { reason, sampled: true }` | Stopped notice, "last reading" body | the last accepted sample, kept (D-03), all messages as for `Live` (suppressions lifted) | `Stopped` |
| `Stopped { reason, sampled: false }` | Stopped notice, "no reading taken" body | `noDiagnostics` (plus any supplied `reading`'s fields), with the suppressions below | `Stopped` |

### Suppressed copy (false while Starting or Stopped)

Before any sample is accepted the reading is `noDiagnostics`, in which `wiring` is `NotHanded`, `activity`
is `[]`, and `hydration`, `portCalls` and `questions` are `undefined`. Several existing messages read an
`undefined` or empty field as "the host did not hand this over", which is false while the dock has been
handed diagnostics and has not read them yet. **The suppressions apply while no sample has been accepted:**
status `Starting`, or `Stopped { sampled: false }`. They are **lifted for `Stopped { sampled: true }`**
(CONTEXT D-02): the reading is then a real sample, so an `undefined` or empty field is a true statement as of
that sample, and every message comes back exactly as it reads for `Live` today. `Off` and `Live` render every
message below exactly as today. Positive data is always shown.

The predicate is one function in `DiagnosticsNotice.tsx`, `isUnsampled(status)`, built with
`Match.tagsExhaustive` (`Starting` true, `Stopped` is `status.sampled === false`, `Off` and `Live` false),
which every row below calls, so the two screens cannot disagree.

A `Starting` that follows a restart may still hold the previous real reading (D-03 keeps it). The
suppressions stay in `Starting` anyway: the neutral replacements are never false over real data, and the
omissions only withhold a negative.

| Screen | Existing copy (testid) | When `isUnsampled(status)` (`Starting`, or `Stopped` with `sampled: false`) | When `Stopped { sampled: true }` | Mechanism |
|--------|------------------------|------|------|-----------|
| Services | "No layer was handed to the dock..." (`qadi-wiring-absent`) | Omitted when `wiring._tag` is `NotHanded`. The notice is the explanation. `Read` and `Failed` render unchanged | Restored: after a real sample `NotHanded` means no layer was configured, which is true | the `NotHanded` arm of `wiringView` is gated on `isUnsampled(status)`, not removed |
| Services | "never called" (`qadi-port-activity`) | When `activity` is empty, reads "no activity reading" instead. When `activity` is non-empty (kept reading after a restart), a port missing from it still reads "never called" | Restored: "never called", true as of the last sample | `PortCard` is given `unsampled: boolean`; one ternary beside the existing one |
| Services | "What each call asked is not shown — pass portCalls..." (`qadi-calls-uncollected`) | Omitted when `portCalls` is `undefined`. A collector may be configured and not yet sampled, and the dock cannot tell which | Restored: `portCalls` undefined after a sample means no collector was handed over, which is true | `RecentCalls` is given `unsampled` and returns `null` for that case |
| Questions | "No atom set was handed to the dock. Pass questions..." (`qadi-questions-absent`) | Omitted when `questions` is `undefined` | Restored: true after a sample | the `questions === undefined` branch is gated on `isUnsampled(status)` |
| Questions | "no counts read. Pass diagnostics={{}} to sample them..." (`qadi-hydration-unwired`) | Replaced by "no counts read yet." with `data-testid="qadi-hydration-pending"`. The advice to pass `diagnostics` would be wrong: it was passed | Not reachable: `hydration` is `undefined` only before the first sample, so a `sampled: true` reading carries it; if a supplied `reading` clears it, the original message returns | the `activity === undefined` branch of `Hydration` is gated on `isUnsampled(status)` |
| Questions | "Nothing has been asked yet..." (`qadi-questions-empty`) | Unchanged. `questions` is `[]` only after a sample returned no questions, so it is true as of the last reading | Unchanged | none |
| Questions | `qadi-gates-absent`, `qadi-keying-note`, `qadi-invalidate` | Unchanged. They depend on host props, not on the diagnostics reading | Unchanged | none |

The wiring-view's `Failed` message and the footer `qadi-activity-scope` paragraph are unchanged.

### Visual hierarchy and focal point

While the status is `Stopped`, **the Stopped notice is the visual anchor of the screen** (Services and
Questions alike). It is the only block on either screen with a tinted background and a coloured border, it
sits first, and its lead phrase is the only amber 600-weight text above the content. The eye lands on it
before the port cards or question rows, which is the point: everything below it has stopped updating, and
the reviewer's one available action (Restart diagnostics) is inside it. The existing amber text on a
defaulted port card (`colors.error`, 11px, no tint, no border) stays a smaller, untinted signal and does not
compete with it.

The **Starting notice is deliberately subordinate**: neutral `colors.border`, no tint, muted text, no
button. Starting is the expected first moment and resolves itself on the next sample, so it must not look
like a fault or take focus from the content that is about to fill in. Amber is spent only on the state that
needs the reviewer to act. The two notices therefore differ in border colour, tint, lead-phrase colour and
the presence of a button, as well as in words, so the difference is never colour alone.

### Starting notice

- Region: `<div role="status" data-testid="qadi-diagnostics-region">`, **always rendered** by
  `DiagnosticsNotice`, with no style of its own, so an empty one adds no visible space. It holds the
  Starting box while the status is `Starting` and is empty otherwise (a live region announces reliably only
  when it exists before its text arrives, so it is never mounted together with its content).
- Element: `<div data-testid="qadi-diagnostics-starting" style={startingNotice}>`, inside the region and
  with no role of its own.
- Style: `panel` spread, `padding: "8px 12px"`, `...muted`, `fontSize: font.size`, no tint, border
  `colors.border`. Deliberately quiet: this is the expected first moment, not a problem.
- Content: lead phrase, then one body sentence (copy below). No button.

### Stopped notice

- Box: `<section data-testid="qadi-diagnostics-notice">`, keyed per stop. Style: `panel` spread,
  `padding: "8px 12px"`, `border: 1px solid colors.error`, `background: withAlpha(colors.error, 0.12)`,
  text `colors.text`, lead phrase `colors.error`.
- Alert: `<div data-testid="qadi-diagnostics-stopped" data-announce="alert|none" data-sampled="true|false">`
  as the box's first child, with `role="alert"` only in the alert mode (see Accessibility); `data-sampled` is
  `String(status.sampled)`. It holds **the lead phrase and the body only**: the reason is a stack trace and
  follows it, outside the alert.
- Content order: alert (lead phrase, body sentence, one of two variants chosen by `status.sampled`, see
  Copywriting Contract), reason block, restart button.
- Reason block, `data-testid="qadi-diagnostics-reason"`, a `<pre>`: `margin: "8px 0 0"`, `padding: 8`,
  `background: colors.surface`, `border: 1px solid colors.border`, `borderRadius: 4`,
  `fontFamily: "inherit"`, `fontSize: font.sizeSmall`, `whiteSpace: "pre-wrap"`,
  `overflowWrap: "anywhere"`, `maxHeight: 96`, `overflow: "auto"`, `tabIndex={0}`, `role="group"`,
  `aria-label="Why diagnostics stopped"`. The reason is `Cause.pretty` output: multi-line, with stack
  frames. It wraps (no horizontal scroll) and scrolls vertically past 96px, never truncated, because a
  reviewer needs to copy it whole. `tabIndex={0}` makes the scroll region keyboard-reachable. Omit the
  block when `reason` is the empty string.
  Note: `WiringRead.Failed` shows its reason inline in a `<p>` (one sentence). `Cause.pretty` is
  multi-line, so this notice uses `<pre>` rather than that inline form; colour, tokens and tone match it.
- Restart button, `data-testid="qadi-diagnostics-restart"`: `<button type="button"
  style={{ ...button(false), marginTop: 8 }} onClick={...}>` with visible text "Restart diagnostics".
  The visible text is the accessible name; no `aria-label` (one that differs from visible text breaks
  voice control). Not `aria-pressed` (a command, not a toggle). The button is in the shared notice, so
  it is available on every screen that renders it.

### Interaction

1. Click or Enter/Space on the button calls `onRestart()`. The feed goes through `Starting` (D-04), so
   the Stopped notice is replaced by the Starting notice and then removed on the first sample. The same
   click works from Services and from Questions.
2. **Focus.** The button unmounts on restart, which would drop focus to `<body>`. The click handler calls
   `onRestart()` and then focuses the screen root: `event.currentTarget.closest("[data-diagnostics-status]")`
   narrowed with `instanceof HTMLElement`, then `.focus()`. This works on any screen carrying
   `diagnosticsRootProps`, needs no ref per screen, and keeps focus inside the panel. The Starting notice's
   `role="status"` carries the announcement.
3. Restart is idempotent: no disabled or pending state. The button leaves the DOM on the first click.
4. No auto-dismiss, no timers, no animation. Notices appear and disappear with status.
5. Hidden `<Activity>` and rebuild (D-06): the model rebuilds at `Starting`, so a screen shows the Starting
   notice on show and nothing from the prior mount. The `announced` ref lives in `DockFrame` inside the
   rebuilt tree, so a stop after a rebuild is announced afresh. This is stated behaviour, not a flicker to hide.
6. `diagnostics` going `undefined` (D-07): status `Off`, no notice, reading reset to `noDiagnostics`.
7. Switching tab between Services and Questions while the status is `Starting` or `Stopped` keeps the
   same reading and the same notice content on both (the screens read one store).

### Accessibility decision: `role="status"` vs `role="alert"`, and once per stop

- **Starting: `role="status"`** (polite), on the always-rendered region. It is the expected first state and
  the reviewer's own action or mount caused it. Interrupting speech for it would be noise. It is not made
  once-only: it is brief and polite. The region is rendered empty for `Off`, `Live` and `Stopped`.
- **Stopped: `role="alert"` the first time a given stop is shown, a plain non-live element after.** A stop
  is a fault that turns a live-looking screen into a stale one with no action by the reviewer, and a
  screen-reader user cannot see the amber, so the first presentation of a stop is assertive. Re-announcing
  the same stop on every revisit to Services or Questions would repeat news the reviewer already has, and
  with two screens it would repeat twice per tab hop, so later presentations are silent: the notice is still
  there to read in browse mode, just not pushed.
- **Mechanism.** "This stop" is the `Stopped` status value itself: each stop produces a new
  `Data.TaggedEnum` value, and the store snapshot keeps its identity until the status changes.
  `DockFrame` owns `announced = useRef(noStops)`, a `StopLedger` (`{ stop, count }`: the last stop a notice
  showed, and how many distinct stops there have been), because it outlives every screen (a screen unmounts
  on tab change, which is exactly the case to survive). The stopped notice decides the mode once per mount
  with `useState(() => announced.current.stop !== status)` (true means `role="alert"`, `data-announce="alert"`;
  false means no role, `data-announce="none"`), and records the stop in a `useLayoutEffect` that writes
  `{ stop: status, count: count + 1 }` when `stop` is not already this status. The notice is **keyed per stop**,
  by `count` when the ledger already holds this stop and `count + 1` when it does not, so a new stop is always
  a new mount and its role is present as the element mounts: a role added to an element already in the tree is
  generally not announced, which is why a second stop that follows a first with no `Starting` render between
  them must remount rather than flip. Fixing the mode at mount keeps the role stable while the notice stays
  mounted, so an unrelated re-render cannot flip `alert` to none and back. Strict Mode's double render and
  double effect are harmless: the initializer sees the same ref, and the effect is idempotent. A new stop
  (`Stopped`, then `Starting`, then `Stopped`, or `Stopped` then `Stopped`) is a new status value and a
  remounted notice, so it alerts again.
- A stop that happens while the reviewer is on a screen with no notice (Log, Inspector, Policies, Roles,
  Simulator) has never been announced, so the first time they open Services or Questions it presents as
  `role="alert"`, which is the correct first announcement. That state is local and is not "React state for
  decisions" (AGENTS.md §13): it records only whether a notice was delivered, never what the reading says.
- Do not put `role="alert"` on the `<pre>` or the button, and do not nest the `<pre>` inside the alert: the
  alert reads the lead and body, not a stack trace. The Stopped notice sets no `aria-live` of its own.
- Contrast: `colors.error` `#e3a008` on `colors.surface` `#14161a` is 8.0:1, and on the amber tint
  background (about `#2d2718`) 6.6:1; `colors.text` on that tint is 12.1:1. `colors.textMuted` `#8b93a3` on
  `#14161a` is 5.9:1 for the Starting notice. All meet 4.5:1 (computed 2026-11-12).
- Focus ring: the dock's existing buttons set no custom outline, so the browser default applies; neither the new
  button nor the screen root sets `outline: none`. The root is focused after a restart, and the browser's own
  ring shows it to a keyboard user.

## Copywriting Contract

Plain, specific, sentence case, no exclamation, no emoji. The panels' existing voice states a fact and
what it means. One copy set serves both screens, because both render the shared notice.

| Element | Copy |
|---------|------|
| Primary CTA | Restart diagnostics |
| Starting lead phrase | Waiting for the first sample. |
| Starting body | Diagnostics has started and has not read anything yet. This screen fills in when the first sample arrives. |
| Empty state heading | Starting lead phrase (the "no data yet" state is `Starting`; there is no separate empty state) |
| Empty state body | Starting body |
| Stopped lead phrase | Diagnostics stopped. |
| Stopped body, `sampled: true` | The sampler failed with an unexpected error and is no longer polling. The reading below is the last one it took and is not updating. |
| Stopped body, `sampled: false` | The sampler failed with an unexpected error before it took a reading, and is no longer polling. Nothing below was sampled by this dock. |
| Error state (reason) | The `Cause.pretty` text, verbatim, in the reason block. Never reworded, truncated or prefixed. |
| Error state (next step) | The Restart diagnostics button. The body sentence names the situation; the button is the way out. If it stops again, the reason names the cause. |
| Reason block accessible name | Why diagnostics stopped |
| Services activity, no reading yet | no activity reading |
| Questions hydration, no counts yet | no counts read yet. |
| Destructive confirmation | none: nothing in this phase is destructive. Restart discards no reading the reviewer holds; the last good reading is replaced only by a fresher one. No confirmation dialog. |

Both notices render a lead phrase followed by the body in one block: lead in `<strong
style={{ fontWeight: 600 }}>`, body in the following text node, separated by a single space.

All "not handed" and "nothing here" copy not listed in "Suppressed copy" is unchanged, and is shown
unchanged for `Off` and `Live`.

## Test Hooks

Following the package's `qadi-…` kebab-case convention (`qadi-wiring-absent`, `qadi-port-state`).

**Shared notice testids are shared, not scoped per screen.** `DevtoolsDock.tsx`'s `Screen` renders
`<>{screens[props.view.tab]()}</>`: exactly one screen is mounted at a time, so a test finds at most one
`qadi-diagnostics-*` element in the dock. A test of a panel on its own also mounts one. A test that wants
to know which screen it is on queries the screen root (`qadi-services` or `qadi-questions`).

| `data-testid` | Element | Present when |
|---------------|---------|--------------|
| `qadi-services` | Services root (existing); gains `data-diagnostics-status`, `tabIndex -1` | always on that screen |
| `qadi-questions` | Questions root (existing); gains `data-diagnostics-status`, `tabIndex -1` | always on that screen |
| `qadi-diagnostics-region` | The polite status region, `role="status"`; empty unless `Starting` | always, on a screen that renders the notice |
| `qadi-diagnostics-starting` | Starting box, inside the region | status is `Starting` |
| `qadi-diagnostics-notice` | The Stopped notice's amber box | status is `Stopped` |
| `qadi-diagnostics-stopped` | The alert element (lead and body only); `data-announce` is `alert` (with `role="alert"`) or `none` (no role); `data-sampled` is `true` (last-reading body) or `false` (no-reading body) | status is `Stopped` |
| `qadi-diagnostics-reason` | `<pre>` with the `Cause.pretty` text, a sibling of the alert inside the box | status is `Stopped` and reason non-empty |
| `qadi-diagnostics-restart` | Restart `<button type="button">` | status is `Stopped` |
| `qadi-hydration-pending` | "no counts read yet." (replaces `qadi-hydration-unwired`) | `Starting` or `Stopped`, `hydration` undefined |

`data-diagnostics-status` takes exactly `Off`, `Starting`, `Live` or `Stopped` (the status `_tag`) on both
roots, so a test can assert `Off` and `Live` render no notice by checking the attribute, the empty region and
the absence of the other notice testids. Tests also query roles: `getByRole("status")`, `getByRole("alert")` (present only on a
first presentation of a stop), `getByRole("button", { name: "Restart diagnostics" })`.

## UI Considerations

Applicable state considerations resolved: 16 covered, 1 backstop, 0 unresolved (probe run 2026-11-12 over five elements: the two notices, the restart button, and the two screens; every proposed category maps to a row below)

| Category | Element(s) | Status | Resolution / Reason |
|----------|------------|--------|---------------------|
| empty | Services and Questions before the first sample | ✅ covered | `Starting` renders "Waiting for the first sample." (see Copywriting Contract) on both screens, never a blank, and the false "not handed" messages are omitted or replaced (see Suppressed copy) |
| loading | Restart in flight | ✅ covered | A restart passes through `Starting` again (D-04), so the same Starting notice is the loading state; no spinner |
| error | Stopped poll, on either screen | ✅ covered | `Stopped { reason, sampled }` renders the notice, the verbatim reason and the restart button (see Copywriting Contract) |
| partial | Stopped before any sample (`sampled: false`) | ✅ covered | The reading is `noDiagnostics`; the notice uses the "before it took a reading" body, so it never calls that reading "the last one it took"; the negative claims about the host stay suppressed (see Suppressed copy) |
| partial | Stopped after a sample (`sampled: true`) | ✅ covered | The notice uses the "last one it took" body, and every suppressed message is restored, because the kept reading is real; `data-sampled` lets a test pin which variant rendered |
| stale | Revisit of a screen while the poll is still stopped | ✅ covered | The notice is shown again on every screen revisit, silent after its first alert, so stale data is never presented without the notice |
| stale | Stop that happens while on a screen with no notice | ✅ covered | The first Services or Questions visit alerts for that stop (the ref only records stops a notice has delivered) |
