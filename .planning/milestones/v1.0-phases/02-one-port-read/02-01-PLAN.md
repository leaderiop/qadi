<objective>
Give each port's span projection one home on its description (`attributes.pose(request)` beside `attributes.disclose(answer, request)`) and send every port read, local or served, through one internal body, `readPort`, in `PortAccess.ts`. Local and served spans of the same question then cannot diverge (D-01, D-03, D-04, D-05, D-06, D-07, D-08).

Purpose: today the served signature span lacks `qadi.meaning`/`qadi.signer_role`/`qadi.matched`, because the projection sat on the wire and was written twice. A served read whose store *throws* also escapes `catchPortDefect` as a defect, because `servedBody` calls `d.invoke(shape)(...args)` outside any wrapped effect. One body removes both defects.

Output: `readPort`; `pose` on all five descriptions; the signature request carries its requirement (`SignatureQuery.meaning`/`signerRole`); `SignatureMatch.ts`; a per-port table in `PortAccess.test.ts`.

- `PortSpanAttributes<Q, Ans, O>` (PortSpan.ts) today has `question: SpanStruct<Q>`, `answer: SpanStruct<Ans>` and `disclose: (outcome: O) => SpanType<SpanStruct<Ans>>`. The member name `question` is taken by the struct, so the new projection member is named `pose`. This is Claude's discretion per CONTEXT. The name `questionOf` is already a different exported function in `Question.ts`, so do not use it. `pose` and `readPort` are unused anywhere in `packages/*/src`.
- `PortDescription.attributes` is typed `Span` (an independent type parameter). A generic `readPort<K>` over `DescriptionOf<K>` cannot call `d.attributes.pose(args)` through `Span` alone: TypeScript distributes `K` and rejects the call. A planning probe showed what does typecheck without `as`: type `attributes` as `Span` intersected with an object type holding only the two functions, `pose: (args: Args) => SpanType<SpanStruct<SpanFields>>` and `disclose: (answer: A, args: Args) => SpanType<SpanStruct<SpanFields>>`, where `Args`/`A` are the description's own parameters. This is the same reason `wire: PortWire<Args, A>` correlates today. Keep the intersected object to the two functions. Do not intersect the `question`/`answer` structs, or `PortTypes[K]["attributes"]["answer"]` and `PortSpanRowOf` stop being exact, and `PortSpan.tst.ts` and devtools' `PortCallOf` rely on that exactness.
- `catchPortDefect` only converts a defect raised *inside* the effect it wraps. Local reads today go through `X.use(...)`, which runs the shape method inside the effect, so a synchronous throw is caught. `servedBody` instead calls `d.invoke(shape)(...args)` directly in the generator. At planning time, `servePortRead(decisionHistoryPort, query)` over `scriptedPort(…, () => PortReply.throw(new Error("boom")))` exited `Failure ["Die"]`, while `askActedAny` over the same layer exited `Failure ["Fail"]`. Wrapping the call as `Effect.flatMap(d.service, (shape) => d.invoke(shape)(...args))` exited `Failure ["Fail"]`.
- Call metrics: `portCallsTotal` (evaluate), `predicatePortCallsTotal` (toPredicate) and `servedPortCallsTotal` (remote) are all `Metric.frequency` over strings. `Metric.update(m, d.port)` compiles for any port name. The guarantee that toPredicate reads only two ports comes from the `ask*` signatures (`Interpreter = Exclude<PortInterpreter, "remote">`), and that alias stays.
- Test helpers: `collectingTracer(spans)` and `isolatedMetrics(effect)` live in `packages/core/test/helpers.ts`. They are core's twins of `@qadi/testing`'s; core cannot depend on `@qadi/testing`. `scriptedPort(d, script).layer` and `.calls`, and `PortReply.answer/fail/die/throw`, come from `src/PortDoubles.ts` and `src/PortDescription.ts`.
